# 实时留痕工具包 v1.0

> 从生命论项目实践中提炼的通用留痕机制。不管干什么，不管做了什么，永远留痕留档，精确到分秒。
> 任何人拿到这个工具包，按说明配置后即可自动使用。

---

## 这是什么

一套解决"AI对话上下文易失、做过的事容易忘、无法追溯历史"问题的工具包。核心思想：

1. **实时commit**：每次文件变化自动git提交，精确到秒的时间戳
2. **运行状态机**：每次启动必读、结束必更的"短期记忆替代物"
3. **代谢日志**：API消耗逐笔记录，先记账再调用
4. **教训库**：每次失败踩坑立即记录，避免重蹈覆辙
5. **冷启动SOP**：每次启动30秒内恢复全部上下文的标准流程

## 快速开始（3步）

### 第1步：把工具包放到你的项目里
```bash
# 把整个"实时留痕工具包"目录复制到你的项目根目录下
cp -r 实时留痕工具包 /path/to/your/project/tools/
```

### 第2步：初始化模板
```bash
cd /path/to/your/project

# 复制运行状态机模板到项目根目录（或你习惯的位置）
cp tools/实时留痕工具包/templates/运行状态机模板.md ./运行状态机.md

# 复制教训库模板
cp tools/实时留痕工具包/templates/教训库模板.md ./教训库.md

# 复制代谢日志模板（如果用API）
cp tools/实时留痕工具包/templates/代谢日志模板.csv ./代谢日志.csv

# 初始化提交日志
bash tools/实时留痕工具包/auto_commit.sh "初始化实时留痕工具包"
```

### 第3步：配置操作人（可选）
```bash
# 在环境变量中设置操作人名字
export OPERATOR="你的名字"

# 或者直接修改auto_commit.sh里的默认值
```

## auto_commit.sh 详细用法

### 单次提交（最常用）
```bash
bash tools/实时留痕工具包/auto_commit.sh "完成了什么事"
```
自动检测变化文件 → git add -A → commit（message带精确时间戳+操作人）→ push → 记录日志。

### 监控模式（自动留痕）
```bash
# 每30秒自动检测并提交一次（默认）
bash tools/实时留痕工具包/auto_commit.sh --watch

# 每60秒自动检测并提交一次
bash tools/实时留痕工具包/auto_commit.sh --watch 60
```
适合长时间运行的任务（如DeepSeek深研、批量处理），保证中间结果不丢失。

### 查看状态
```bash
bash tools/实时留痕工具包/auto_commit.sh --status
```
显示：当前git状态、最近5条提交、最近10条提交日志。

### commit message格式
```
[2026-09-01 14:30:25] 明旭：完成了L3类型规则设计
```
- 精确到秒的时间戳
- 操作人名字
- 你写的说明

### 提交日志（commit_log.csv）
每次提交自动记录：
| 字段 | 说明 |
|------|------|
| 时间 | 精确到秒 |
| 操作人 | 谁提交的 |
| 操作类型 | commit/watch/status |
| 文件数 | 变化了多少个文件 |
| commit_hash | 提交哈希 |
| 状态 | 成功/push失败/无变化 |
| 备注 | 你写的说明 |

## 运行状态机使用方法

### 为什么需要
AI对话上下文会被压缩、丢失。下一次启动时可能完全忘了上一次干了什么。运行状态机就是"外置记忆"——把当前进度、配置、教训、待办全部写在文件里，每次启动第一个读它。

### 怎么用
1. **启动时**：第一个动作就是读`运行状态机.md`，30秒内恢复全部上下文
2. **执行中**：每完成一个阶段，在"正在运行"中更新进度
3. **结束时**：最后一个动作就是更新状态机——把任务从"正在运行"移到"已完成"，记录产出和commit hash，更新待办

### 核心结构
- **最近更新**：时间、更新者、触发事件
- **当前迭代进度**：已完成/正在运行/待执行（三张表）
- **关键配置与参数**：API配置、产出目录、核心原则
- **任务调度与冲突解决**：启动前检查、长任务心跳、提前完成处理
- **最近教训**：最近5条（完整记录在教训库）
- **未完成事项与待办**

## 代谢日志使用方法（如用API）

### 原则：先记账再调用
每次API调用前，先在CSV中记录一行（时间、模型、对象、预估输入），调用后补充输出和状态。这样即使调用失败，也有痕迹。

### CSV字段
| 字段 | 说明 |
|------|------|
| 时间 | 精确到秒 |
| 操作人 | 谁调用的 |
| 模型 | 用的什么模型 |
| 档位 | A档深研/B档结构化 |
| 对象 | 调用目的（如"L3类型规则设计"） |
| 缓存命中输入 | 前缀缓存命中的token数 |
| 未命中输入 | 实际计费的输入token |
| 输出 | 输出token数 |
| 重试次数 | 重试了几次 |
| 状态 | 成功/失败/超时 |
| 耗时秒 | 调用耗时 |
| 备注 | 其他说明 |

## 教训库使用方法

### 原则：每次踩坑立即记录
不要等"以后再补"，立即记录。根因分析要挖到最底层，预防机制必须是可操作的具体步骤，不是"以后注意"这种空话。

### 记录格式
每条教训包含：
1. **时间**：精确到分
2. **错误描述**：具体发生了什么
3. **根因分析**：3条以内，挖到最底层
4. **修复措施**：采取了什么措施
5. **预防机制**：以后怎么避免，可操作的具体步骤
6. **对项目的启示**：更深层的启示

### 编号规则
L + 三位数字（L001, L002, ...），按时间顺序递增，永不复用。

## 冷启动SOP使用方法

每次启动（包括定时任务触发）时，按10步执行：

| 步骤 | 动作 | 目的 |
|------|------|------|
| 0 | 获取真实时间 | 所有时间戳的基准 |
| 1 | 读运行状态机 | 恢复全部上下文（最重要） |
| 2 | 读启动必读卡片 | 确认身份和原则 |
| 3 | 读代谢日志 | 知道最近API消耗 |
| 4 | 读教训库最近3条 | 避免重蹈覆辙 |
| 5 | 检查git状态 | 确认是否有未提交变化 |
| 6 | 检查正在运行的进程 | 避免重复启动 |
| 7 | 确认当前任务 | 从待执行列表取优先级最高的 |
| 8 | 执行任务 | 按要求执行，过程中更新状态机 |
| 9 | 更新状态机 | 最后一个动作，记录完成情况 |
| 10 | 自动提交 | 确保所有变化已提交push |

## 与定时任务配合

如果用定时任务（cron），每个任务的prompt里应该包含：

```
【启动SOP·铁律】
1. 读运行状态机 → 恢复上下文
2. 读明性卡片/启动必读 → 确认身份和原则
3. 读代谢日志 → 知道API消耗
4. 读教训库最近3条 → 避免重蹈覆辙
5. 执行当前任务
6. 更新运行状态机 → 记录本轮做了什么
7. git add/commit/push → 沉积
```

## 设计原则

1. **精确到秒**：所有时间戳精确到秒，不用"今天""刚才"这种模糊表述
2. **先记账再行动**：代谢日志先记再调，状态机先读再干
3. **启动必读，结束必更**：状态机是唯一权威来源
4. **失败不破坏库**：auto_commit.sh失败时不删除任何文件，只记录日志
5. **可移植**：不依赖特定项目结构，放到任何git仓库里都能用
6. **零配置可用**：复制过去就能用，高级功能才需要配置

## 常见问题

### Q: 监控模式（--watch）会不会产生大量无意义commit？
A: 不会。脚本会检测是否有文件变化，无变化时跳过提交。只有真正有变化时才提交。

### Q: push失败怎么办？
A: 本地commit不会丢失，push失败时记录到日志，稍后重试。可以在状态机中标记"push失败待重试"。

### Q: 可以用在非git项目吗？
A: auto_commit.sh依赖git，但运行状态机、代谢日志、教训库、冷启动SOP不依赖git，可以单独使用。

### Q: 怎么和DeepSeek/其他API配合？
A: 代谢日志模板就是为API消耗追踪设计的。每次调用前先记账，调用后补充输出和状态。运行状态机的"关键配置"部分记录API参数。
