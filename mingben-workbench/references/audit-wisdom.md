# 代码审计智慧录：从"查过了"到"跑过了"

> 核心教训：**说"查过了没有bug"是最不可信的保证。唯一可信的是：每条代码路径都在沙箱里实际执行过，且执行前后的不变量都被验证过。**

## 一、四层验证模型

代码验证有四个层次，每一层只能发现该层的问题，不能替代下一层：

| 层次 | 问什么 | 怎么查 | 能发现什么 | 发现不了什么 |
|------|--------|--------|-----------|-------------|
| L1 语法 | 能不能跑 | `bash -n` / `py_compile` | 拼写错误、语法错误 | 逻辑错误 |
| L2 状态 | 当前状态对不对 | self_audit.py 13项检查 | 文件缺失、数字不一致、引用失效 | 操作逻辑错误 |
| L3 逻辑 | 做得对不对 | 人工追踪执行路径、反面推导 | 升序碰撞、跨模块遗漏、stale position | 未想到的边界条件 |
| L4 执行 | 真跑一遍对不对 | test_system.py 沙箱测试+不变量验证 | 所有实际触发的bug | 测试未覆盖的路径 |

**关键认识**：L1-L3都是"静态"的——读代码、查状态、推逻辑。L4是"动态"的——在隔离环境中真跑。auto_merge.py的三个严重逻辑bug通过了L1-L3的多轮检查，但在L4第一次运行时就暴露了。原因很简单：**那个代码路径从来没被实际执行过**（所有章节都是追加的，从未在中间插入过）。

## 二、不变量思维

不要测"输出是什么"，要测"输出必须满足什么"。

好的不变量：
- **章节编号1..N连续无重复**——不管怎么插入/替换/顺延，这个必须成立
- **renumber前后标题集合不变**——只是编号偏移，标题不能丢、不能错
- **交叉引用必须指向存在的章节**——顺延后引用必须跟着更新
- **插入操作后总章数+1，替换操作后总章数不变**

不变量比具体断言更强大：一个不变量可以覆盖无数种输入组合。你不需要穷举所有测试用例，只需要定义"什么状态是正确的"，然后让机器验证。

## 三、沙箱测试法

在临时目录中构造最小但完整的系统，执行真实操作，验证结果：

1. **构造**：创建临时目录，放入最小化但结构完整的测试数据（3个文件×2章=6章，而非252章）
2. **执行**：调用真实脚本（不是mock，不是模拟，是真跑）
3. **验证**：解析输出，检查不变量
4. **销毁**：删除临时目录，不留痕迹

沙箱测试的关键是"最小但完整"——数据量小到可以人肉验证结果，但结构完整到能触发所有代码路径（多文件、多章节、跨模块引用）。

## 四、注入测试法

验证检查器本身是否有效：不要只测"正确的东西能通过"，还要测"错误的东西能被抓到"。

- 注入错误章数（252→999）→ 自筛必须报"章数不一致"
- 注入失效引用（一个不存在的脚本路径（如scripts/nonexistent.py））→ 自筛必须报"失效引用"
- 注入交叉引用越界（"参见第九十九章"）→ 自筛必须报"交叉引用越界"
- 注入null字节、编号重复、标题跳跃 → 质检必须抓到

**一个检查器如果只能验证正确状态、不能识别错误状态，它就是装饰品。**

## 五、递归审计：谁监督监督者

self_audit.py 监督其他脚本，但 self_audit.py 自己也有盲区：
- 初版只扫一个技能目录，漏了 mingben-output
- 初版对命令式引用（命令式调用中的脚本路径）直接跳过，不检查文件是否存在

这是 S=f(S) 的递归：**审计者本身也必须被审计**。方法是：
1. 用注入测试验证审计者能抓到问题
2. 定期用L4执行测试覆盖审计者自身的代码路径
3. 每次发现审计者的盲区，就把盲区变成新的检查项

## 六、本轮发现的bug模式总结

| bug | 根因 | 教训 |
|-----|------|------|
| 升序顺延导致标题碰撞 | 5→6后文本出现两个"第六章"，下次replace命中已改名的标题 | 批量重命名必须降序处理 |
| 跨模块引用不更新 | 只在包含章节的模块替换引用 | 全局影响必须全局扫描 |
| 插入位置用旧坐标 | renumber后文本长度变化，旧坐标失效 | 修改后必须重新定位，不能用stale position |
| 替换vs插入无法区分 | 编号存在即替换，但中间插入时编号也存在 | 同标题=替换，不同标题=插入 |
| 自筛漏扫目录 | 只硬编码了一个技能目录 | 扫描范围应自动发现 |
| 命令式引用跳过检查 | 命令式调用中的脚本路径被当作命令跳过 | 从命令中提取文件路径再检查 |
| backup.sh漏打包文件 | tar列表手动维护，新增文件忘记加 | 打包列表应自动发现或有测试验证 |
| publish.sh无门控 | 发布前不跑自筛 | 所有破坏性/外部操作前必须有硬门控 |

## 七、与小本质递归法的对接

小本质递归法用于代码审计的流程：

1. **抓小本质**：从最具体的函数/循环下手（auto_merge.py的renumber循环），不泛泛而谈
2. **反面推导**：问"这个操作在什么条件下会出错？"（升序→碰撞；跨模块→遗漏）
3. **冲和**：静态审查能发现逻辑问题但覆盖不全，动态测试能验证行为但只能覆盖想到的场景——两者必须结合
4. **上推根因**：根因不是"这行代码写错了"，而是"未被执行的路径不可信"
5. **下行统摄**：从根因出发，所有脚本都需要L4执行测试，不只是出问题的那个
6. **交叉印证**：人工逻辑推导 + 沙箱实际执行 + 注入测试，三重验证
7. **动态边界**：不可能100%保证没有bug，但可以保证：所有代码路径都被执行过、所有不变量都被验证过、检查器本身被注入测试验证过

## 八、确保机制（当前状态）

```
改代码 → bash -n/py_compile (L1语法)
       → build.sh --html-only (L2状态+构建)
       → self_audit.py 14项 (L2状态+L4执行)
         ├── 13项静态检查
         └── 1项功能测试套件 (29个测试用例，沙箱实跑)
       → sync.sh 推送 (硬门控：以上全过才push)
```

这套机制不依赖任何人"记住要检查"，而是在构建和推送时自动执行。测试套件覆盖：
- 中文数字转换1-299往返+边界值
- auto_merge：追加/中间插入/替换/第1章边界/跨模块引用更新
- self_audit：4种注入问题必须被抓出
- build.sh质检：5种错误必须被抓出+未知参数拒绝
- replace.sh：--add正确插入到卷区域而非末尾

**这不是"我觉得没有bug了"，是"每条路径都跑过了，每个不变量都验证过了，每个检查器都被反向测试过了"。**
