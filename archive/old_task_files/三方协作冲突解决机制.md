# 践演论三方协作冲突解决机制

> **用途**: 明确豆包/DeepSeek/WorkBuddy三方同时修改同一文件时的处理流程，避免冲突和覆盖。
> **最后更新**: 2026-08-26
> **维护者**: 豆包（总控）

---

## 一、三方角色与权限

| 角色 | 权限 | 负责领域 | 分支 |
|------|------|---------|------|
| **豆包**（总控） | push main + 审查合并 + 最终裁决 | 数学发明、哲学解读、综合论文、质量把控、三方协调 | `main` |
| **DeepSeek**（代码/形式化） | push 自己分支 + PR | Coq形式化、类型检查器开发、代码修复 | `deepseek/*` |
| **WorkBuddy**（审计/反例） | push 自己分支 + PR | 反例攻击、新颖性核查、学术规范改写、Coq代码审计 | `workbuddy/*` |

## 三、冲突处理流程

### 场景1：同时修改同一文件

**检测**: git push时被拒绝（non-fast-forward），或PR合并冲突

**处理流程**:
1. **停止操作**，不要force push
2. **git pull** 获取最新版本
3. **手动解决冲突**:
   - 如果是自己分支的冲突：自己解决
   - 如果是main分支的冲突：通知豆包，由豆包裁决
4. **解决后重新测试**：运行检查器+验证脚本
5. **重新提交**

### 场景2：覆盖了别人的修改

**检测**: 别人发现自己的修改不见了，或git log显示异常

**处理流程**:
1. **立即停止**，不要继续修改
2. **git reflog** 找到被覆盖前的commit
3. **git cherry-pick** 恢复被覆盖的修改
4. **通知相关方**，说明发生了什么
5. **按场景1重新合并**

### 场景3：对同一问题有不同方案

**检测**: 两方提出了不同的解决方案，无法直接合并

**处理流程**:
1. **各自在自己分支实现方案**
2. **写对比文档**：各自方案的优缺点、证明难度、哲学一致性
3. **豆包裁决**：基于第一性原理底线和弱版优先原则选择
4. **被选中的方案合并到main**，未选中的保留在分支作为参考

## 四、分支策略

### 分支命名规范

```
main                          # 主分支，只有豆包能push
deepseek/coq-layer2           # DeepSeek的Coq第2层工作
deepseek/type-checker-fix     # DeepSeek的类型检查器修复
workbuddy/round3-attack        # WorkBuddy的第三轮反例攻击
workbuddy/academic-rewrite     # WorkBuddy的学术改写
```

### 合并流程

1. **在自己分支工作**，完成后运行所有检查器和验证脚本
2. **更新任务监控表**，标记任务完成
3. **通知豆包**："我完成了XXX，在分支XXX，请审查合并"
4. **豆包审查**：
   - 检查代码/文档质量
   - 运行检查器和验证脚本
   - 确认符合第一性原理底线
   - 确认没有越级陈述
5. **豆包合并到main**，或要求修改后重新提交

### Force Push规则

- **main分支**: 绝对禁止force push
- **自己的分支**: 可以force push，但必须通知其他人
- **别人的分支**: 绝对禁止force push

## 五、争议解决机制

### 争议等级

| 等级 | 描述 | 解决方式 |
|------|------|---------|
| L1 | 技术细节（命名、格式、代码风格） | 各自按自己的习惯，豆包统一规范 |
| L2 | 方案选择（两种不同的实现方式） | 各自实现，对比文档，豆包裁决 |
| L3 | 数学正确性（定理是否成立） | 反例攻击+Coq形式化验证，以证明为准 |
| L4 | 哲学方向（是否符合践演论核心直觉） | 回到第一性原理底线，用户最终裁决 |

### 裁决原则

1. **第一性原理底线优先**：任何方案不能违背践演论核心直觉
2. **弱版优先**：先证满射↠/retraction⇒/双模拟≈，能升回≅的再升
3. **可验证优先**：能Coq形式化的方案优先
4. **哲学一致性优先**：与生命论哲学一致的方案优先

## 六、日常协作规范

### 提交前检查清单

每次commit前，自动运行（pre-commit hook）：
- [ ] 生成项目状态报告
- [ ] 运行越级陈述检查器
- [ ] 运行引用一致性检查器
- [ ] Coq代码：运行coq_verify.py --strict
- [ ] Python代码：运行单元测试（如果有）

### 提交信息规范

```
[作者] 类型: 描述

作者: doubao / deepseek / workbuddy
类型: feat（新功能）/ fix（修复）/ docs（文档）/ refactor（重构）/ test（测试）/ infra（基础设施）

示例:
[doubao] feat: 新增T019明性不动点定理
[deepseek] fix: 修复ren_typed定理Coq证明
[workbuddy] docs: 第三轮反例攻击报告
```

### 通知机制

完成任务后，在对话中通知豆包：
```
✅ 完成: [任务ID] 任务描述
   分支: branch-name
   变更: 修改了X个文件，新增Y个定理
   验证: 检查器通过，Coq验证通过
   待审查: 请豆包合并到main
```

## 七、紧急情况处理

### 数据丢失

1. **立即停止所有操作**
2. **检查backup/目录**，看是否有最近的备份
3. **git reflog** 找到丢失前的commit
4. **恢复数据**，通知所有方
5. **分析原因**，更新机制防止再次发生

### 冲突无法解决

1. **暂停相关工作**
2. **写冲突描述文档**：冲突是什么、各方立场、影响范围
3. **用户裁决**：最终由用户决定方向
4. **按裁决执行**，更新机制
