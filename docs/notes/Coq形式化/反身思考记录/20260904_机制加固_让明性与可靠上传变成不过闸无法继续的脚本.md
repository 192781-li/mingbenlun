# 反身思考：机制加固——让"明性"和"可靠上传"变成不过闸就无法继续的脚本

时间：2026-09-04
分站：S04（明序）
触发：主人要求"再多做几轮，确保真正落实、避免以前种种让人生气的谬误，尤其再也不要出现'别的对话轻松 GitHub 上传、你却很难做到'；始终保持明性"。

## 一、这轮的本质判断

主人不要"我下次一定注意"的保证书——那种东西在连续对话被压缩后必然失效（教训 L035 已钉死：能机械化的智慧必须改写成不过闸就无法继续的函数，否则等于没有）。所以这轮只做一件事：**把历史上每一个让主人生气的坑，逐条翻译成代码里绕不过的机制**。

## 二、历史谬误 → 代码机制 的逐条映射

| 历史上反复犯的错 | 根因 | 本轮落地的机制（不是口号） |
| --- | --- | --- |
| 别的对话轻松 push、S04 却反复失败 | origin 是 SSH，22 端口被封；schannel 吊销 0x80092012；PowerShell 裸 git 报错；token 每次手拼 | `s04_git.py`：固定 PortableGit 全路径 + openssl 后端 + https URL 绕 SSH + 自动读 token（不回显）+ push 正确成功判据（rc≠0 但已出现 `-> branch` 也算成功）+ 失败重试 3 次 + save 一条龙 + 推完校验本地==远程 |

| 在错误分支提交 | 不查当前分支 | save 前强制 `cur_branch()==s04-coq`，否则拒绝 |

## 三、建设过程中，自检亲手抓出自己两个 bug（"做一遍检查一遍"的实证）

1. **Admitted 正则漏报**：第一版写 `Admitted\s\.`（要求词与点间恰好一个空格），真实代码是 `Admitted.`（无空格），导致自检报"L2=0"——自检脚本自己差点成了闭环短路。实测才暴露，改 `\s*` 后准确报出 L2=1。**教训：保障机制本身也必须被运行验证，写出来不等于有效。**
2. **Layer3 假绿**：一直以为"Layer3 0 Admitted 骨架绿"，--deep 一编译，580/592 行 `eapply subject_reduction` 找不到——Layer2 根本还没证出 subject_reduction。定性为**跨层依赖未就绪（WARN），不是本轮回归**；机制上用条件门表达：L2 未清零时 L3 失败是预期待办，L2 清零后 L3 必须转绿，否则才是真 FAIL。既不假装绿，也不警报疲劳。

## 四、明性反思

- 明性不是"我记得我在干什么"，而是**随时有一面不靠记忆的镜子**照出真实状态：分支对不对、编译绿不绿、洞还剩几个、双门在不在、本地和远程一不一致。preflight 就是这面镜子，且它必须可执行、可重复、会亮红灯。
- 可靠上传的本质是**消除对临场状态的依赖**：不依赖 PATH 里有没有 git、不依赖这次走 SSH 还是 https、不依赖我记不记得 token 放哪、不依赖 returncode 的假象。这些全部固化进 s04_git.py 后，任何一轮新对话（哪怕上下文被压缩干净）一条 `save` 就能和"别的对话"一样轻松上传。
- 这轮没有写一行证明 tactic（split_assoc 仍 Admitted，留 DS 主谋），因为本轮的任务对象是"我自己的操作范式"——把地基夯实，比急着往上砌一块可能歪的砖更重要。

## 五、固化后的标准动作（已写入唯一权威 SOP 铁律第 6 条）

- 开工：`python scripts/s04_deepseek/s04_git.py sync`
- 收工：`python scripts/s04_deepseek/preflight.py --deep`（红灯不许提交）
- 提交：`python scripts/s04_deepseek/s04_git.py save -m "..." [显式新文件...]`
