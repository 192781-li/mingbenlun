## 十三、保障措施（可执行检查清单）

> 原则：**能机械化的必须写成代码/脚本，不能只靠"记住"。** 每条措施都有触发条件、执行动作、验证方法。

### 13.1 导航地图自身保障

| 措施 | 触发条件 | 执行动作 | 验证方法 |
|---|---|---|---|
| 版本递增 | 每次S05巡检发现结构变化 | 目录地图/进度报告版本号+1，旧版归档 | `ls docs/notes/信息分站/` 确认最新版 |
| 路径失效检测 | 任何分站报告"文件找不到" | 用 `find . -name "文件名"` 实测，更新地图中路径 | 失效路径数=0 |
| 一致性校验 | 每周一次 | `find . -type f -not -path './.git/*' \| wc -l` 与地图标注比对 | 差异<5% |
| 索引更新 | 新增/删除>10个文件 | 更新本地图对应章节 + `INDEX.md` | git diff 包含索引更新 |

### 13.2 库操作安全保障

#### Git操作规范
- **提交前必查**：`git status` 确认没有误删/误改非目标文件
- **提交信息**：必须写清"谁+做了什么+为什么"，禁止 `update` / `fix` 等无信息提交
- **推送频率**：同类操作合并为一次commit，避免频繁push（用户明确要求）
- **冲突处理**：
  - 配置文件(.json)冲突 → 手动合并后 `python3 -c "import json;json.load(open('文件'))"` 验证格式
  - Coq代码(.v)冲突 → **不擅自解决**，标注后报告S04
  - 文档冲突 → 保留双方内容，标注差异

#### 大文件监控（强制）
| 阈值 | 动作 | 责任方 |
|---|---|---|
| >5M 新文件出现 | 立即迁移到档案库，主库留INDEX.md | 发现者（任何分站） |
| 2-5M 文件 | 评估是否为中间产物，是则删除/迁移 | S05巡检标注 |
| 仓库>80M | 报警，启动大文件治理 | S05 |
| 仓库>100M | 紧急治理，暂停新增大文件 | S00+S05 |

**验证命令**：
```bash
find . -type f -not -path './.git/*' -size +5M  # 应返回0
du -sh --exclude=.git .  # 应<80M
```

#### .gitignore 强制规则
```
*_monitor_logs/
*_check_logs/
*_temp_docs/
__pycache__/
*.pyc
*.tmp
*.bak
```

### 13.3 分站运行保障

#### 休眠/激活判断标准
| 状态 | 判断条件 | 动作 |
|---|---|---|
| 活跃 | 最后提交<3天 | 正常运行 |
| 休眠 | 最后提交3-7天 | 不主动激活，标注休眠 |
| 长休眠 | 最后提交>7天 | S05报告，由用户决定是否激活 |
| 异常 | 分支领先main>3且无PR | 标注"建议合并" |
| 脱节 | 分支落后main>10 | 标注"需同步" |

**用户明确偏好**：分站休眠是正常的，不需要主动激活。重叠的工具/内容要融合，不启动新号。

#### 分站产出质量门

## 十四、分域保障：不同地方的专属规则与手法

> 原则：**每个地方有每个地方的打法，不搞一刀切。** 以下规则来自实测教训和已验证手法，不是口号。

### 14.1 S00 大总站（协调者）

**核心规则**
- 唯一注册中心：分站身份、分支、token、定时任务的权威来源是 `定时任务网络配置.json`
- PR审核三看：看commit message是否写人话、看是否有具体产出、看配置是否更新
- 合并顺序：先合无冲突的，再合有冲突的；冲突只改配置和文档，Coq代码(.v)冲突不擅改
- 不替分站干活：分站的工作分站自己做，S00只协调、审核、合并

**最佳手法**
- 合并前先 `git log origin/<branch> -3 --oneline` 看最新产出
- 合并后立即更新 `明旭_运行状态机.md` 和网络配置
- 多分站同时活跃时，用 `分站间协作完整案例_T007命名修改_可复制模板.md` 的流程

**常见错误**
- ❌ 不看产出就合并 → 合入低质量/重复内容
- ❌ 替分站写代码 → 越位，分站失去成长机会
- ❌ 合并后不更新状态机 → 其他分站信息不同步

**验证标准**
- 合并后 `git log main -1` 有明确的合并说明
- 状态机和网络配置版本号递增

### 14.2 S01 哲学分站（研究者）

**核心规则**
- 哲学为骨：所有概念辨析必须回到存在论/认识论根基，不做无根的概念游戏
- 东方为骨西方为体：命名审查时，东方概念（感/应/明性/迹）为骨架，西方术语为参照
- 为Coq服务：哲学研究的最终产出是能被S04形式化的精确定义，不是纯文字

**最佳手法**
- 给S04的证明策略要"精确到tactic级别"（如 `S01给S04_typar收尾完整证明策略_精确到tactic级别`）
- 一个引理一个策略文档，不混写（`S01给S04_DeepSeek逐个证明指令包_4个引理一次只证一个`）
- 概念辨析用"存在论分析"格式：是什么→从哪来→怎么运作→和什么关联
- 代表作：`S01_在感的存在论分析`、`S01_迹的存在论分析`、`S01_生的存在论分析`

**常见错误**
- ❌ 写纯哲学散文，不给S04可操作的定义
- ❌ 概念定义模糊，S04无法形式化
- ❌ 和S04重复劳动（S04已经证明的，S01又重新研究）

**验证标准**
- 每篇哲学研究有明确的"可形式化结论"段落
- S04能直接引用S01的定义写Coq代码

### 14.3 S02 高考文科分站（写作者）

**核心规则**
- 全本写作：唯一可改正文是 `生命论_模块化/`，不在其他地方写正文
- 文体统一：全本用同一种文体强度，不忽硬忽软
- 文字润色：润色不改意思，只改表达

**最佳手法**
- 用 `doubao-book-writer` skill 处理长文档
- 篇章修改后立即commit，标注"改了哪篇、为什么改"
- 参考 `明本学术法`（卷四篇六）的自指五环闭环：提问→检索→精读→写作→引用审计

**常见错误**
- ❌ 在docs/notes/里写正文 → 正文必须在 `生命论_模块化/`
- ❌ 润色时改了原意 → 阴主阳从
- ❌ 一次改太多篇 → 无法review

**验证标准**
- 正文只在 `生命论_模块化/` 下
- 每次commit只改1-3篇，有明确说明

### 14.4 S03 术数分站（翻译者+批判者）

**核心规则**
- 核心价值是"翻译"和"批判"，不是宿命论
- 术数不是宿命论是结构论：α+T是过去操作的沉积，N是当前操作，M是操作总和
- 阳主阴从：操作（N）主导，结构（α+T）从属

**最佳手法**
- 用量论公式 M=α·T·N 重新解释术数概念（身弱不胜财、命好不如运好等）
- 排盘工具用 `tools/术数工具包/`（奇门/八字/六壬）
- 术数研究产出放 `docs/术数研究/`

**常见错误**
- ❌ 搞宿命论宣传 → 违反项目核心理念
- ❌ 只排盘不翻译 → 没有哲学价值
- ❌ 和S00重复研究三元九运 → 先查库

**验证标准**
- 每篇术数研究有"生命论翻译"段落
- 不出现"命中注定""不可改变"等宿命论语调

### 14.5 S04 Coq形式化分站（工程师+主谋协同者）

**核心规则（DS V4范式，唯一权威）**
- **DeepSeek是主谋**：拥有发现权、规划权、引理设计权、完整证明书写权
- **S04只保留两项权**：①本地coqc执行与git操作；②数学认知与S01哲学联动的分析桥梁
- **S04不自己写任何tactic**，不起念"我先试试改一个字"
- **数学对错的终裁是coqc**，不是DS的自信、不是S04的感觉

**最佳手法（已验证）**
- **全量喂上下文**：Layer1+2+3全文（~49K token）全量喂入，占1M窗口4.9%，第二轮起缓存命中不到1分钱
- **四层稳定→变化**：system前缀→稳定材料（全文）→追加历史→本轮变化（目标+coqc错误原文）
- **小步流水线**：一个引理一个脚本，先交定义+小引理，coqc固化后再交主定理（`run_j1_split_assoc.py` 的INSERT-BEFORE机制）
- **证伪守卫双门**：任何"命题为假/反例"必须过 `falsification_guard.py`——①反例独立coqc exit=0；②反向exists压测。双门不过默认为真
- **证明循环**：`proof_loop.py` 自动 build_messages→DS→抽coq→来源标签分流/编造校验/卫生检查→coqc→回喂
- **看板取活**：`board.py` 自动从看板取任务、完工回填，杜绝凭记忆/重启空转

**参数铁律（教训L034）**
- 模型：`deepseek-v4-pro`（证明主用）+ `deepseek-v4-flash`（结构化杂活）
- max_tokens：证明任务≥32000（上限384K），开自动续写
- thinking：证明用enabled，纯格式转换用disabled
- 不凭记忆设参数，先查官方文档+小成本实测

**常见错误（教训L034/L035）**
- ❌ 只喂相关几百行 → 128K窗时代的自我设限，已被实测否定
- ❌ max_tokens给8192 → 思维链吃光额度，正文空输出（不是被掐断）
- ❌ DS说命题为假就盲信 → 必须过证伪守卫双门（split_assoc事故：DS反例option双层错层，定理实际为真）
- ❌ coqc报错就用自然语言推理替代 → 严禁，先修到能编译
- ❌ S04自己手改tactic → 越位，必然损耗信息
- ❌ 多份矛盾的DS方法论并存 → 唯一权威文档取代，旧文档归档

**验证标准**
- 每个证明目标有对应的 `run_*.py` 脚本
- coqc exit=0 才算证明完成
- 改工具链后必跑 `falsification_guard/proof_loop/s04_context` 三连离线自检

### 14.6 S05 信息分站（神经系统）

**核心规则**
- 让信息流动：所有分站知道全局状态
- 不替分站做决策：只报告状态、标注异常、建议行动
- 库整洁是底线：大文件监控、目录地图、去重整合

**最佳手法**
- **每日巡检四步**：同步→进度报告→目录地图（仅当变化）→跨分站检查→提交
- **大文件治理**：>5M立即迁移档案库，主库留INDEX.md；迁移用 `git mv` 保留历史
- **库整理三原则**：旧版归档（archive/old_editions/）、临时日志归档（archive/temp_logs/）、重复文件去重
- **工具融合**：重叠工具不并存，融合为一个最新版，删除旧的（如video_transcriber v2.0融合bilibili_transcriber）
- **导航维护**：版本递增、路径失效检测、一致性校验

**常见错误**
- ❌ 频繁GitHub操作 → 用户明确要求不要过多频繁，同类操作合并为一次commit
- ❌ 擅自删除分站工作文件 → 只归档，不删除；中间产物需确认后再删
- ❌ 报告只列数据不分析 → 要标注活跃/休眠、阻塞点、建议行动
- ❌ 和其他分站重复劳动 → 先查库，S00已经做的导航不重复造

**验证标准**
- 仓库<80M，>5M文件=0
- 每日巡检有进度报告+目录地图（如有变化）
- 信息分站目录只有最新版+专题报告+索引

### 14.7 写正文/学术生产（通用）

**核心规则**
- **阳主阴从**：活的思想是阳，工具/规范/模板是阴，阴服务阳
- **实先于名**：先有内容，后有位置，位置为内容服务
- **不硬融**：投喂的硬核文本和现有内容不兼容时，单独存放作为更高强度版本，不强行揉合

**最佳手法**
- **明本学术法五环闭环**（卷四篇六）：提问→检索→精读→写作→引用审计，每环输出可回溯修正前环
- **归位规则**（`归位规则手册 v1.3`）：文件类型→目录映射表，.md→docs/，.py→scripts/，图片按用途分visualizations/assets/reference_materials
- **硬核文本处理**：不硬融、大胆的整、不怕冲突（git有历史）
- **文档元数据标准**（`文档元数据总标准 v1.0`）：每个文档有标题、版本、日期、作者、状态

**常见错误**
- ❌ 为了发论文而找问题 → 学术异化（阴主阳从）
- ❌ 为了凑引用而读文献 → 工具反过来支配研究者
- ❌ 正文写在docs/notes/里 → 违反归位规则
- ❌ 一次改太多篇 → 无法review

**验证标准**
- 正文只在 `生命论_模块化/`
- 每个文档有元数据头
- 文件位置符合归位规则映射表

### 14.8 做研究/防重复（通用）

**核心规则**
- **研究前先查**（铁律，顺序不可颠倒）：
  1. 查 `02_问题反查总表` → 命中就去指定文件提取，不开研究
  2. 查 `01_编号映射总表` → 是不是旧定理换了名字
  3. grep本地库原文 → 确认是否真空
  4. 只有 `03_真前沿清单` 或逐文件确认无答案 → 才允许动用DeepSeek
- **不重复造轮子**：库里已有的答案，直接引用，不重新研究

**最佳手法**
- 用 `theorem_id_mapping.json` 机查编号映射
- 用 `grep -r "关键词" --include="*.md" .` 快速定位
- 研究产出放 `docs/notes/` 对应子目录，不放根目录

**常见错误**
- ❌ 只喂简化材料让DS研究 → 结果重新发现库里早有的更成熟版本（8/31教训）
- ❌ 不查库就开研究 → 浪费算力+重复劳动
- ❌ 研究产出乱放 → 找不到，下次又重复

**验证标准**
- 研究前有"查库确认"记录
- 研究产出在正确目录，有元数据

### 14.9 用工具/脚本（通用）

**核心规则**
- **重叠工具搞融合**：不并存两个功能重叠的工具，融合为一个最新版
- **工具为任务服务**：不为了用工具而用工具
- **脚本有说明**：每个工具目录有README/使用说明

**最佳手法**
- 融合时保留两个工具的所有功能，删除旧的（如video_transcriber v2.0）
- 通用脚本放 `scripts/`，分站专属脚本放 `scripts/s04_deepseek/` 等子目录
- 旧版本归档到 `archive/old_editions/`，不删历史

**常见错误**
- ❌ 两个工具功能重叠还并存 → 用户困惑用哪个
- ❌ 脚本没有使用说明 → 别人不会用
- ❌ 临时脚本不清理 → 库膨胀

**验证标准**
- 无功能重叠的工具并存
- 每个工具目录有说明文档

### 14.10 运维/协作（通用）

**核心规则**
- **Token不写入库**：用环境变量或git credential，绝不commit token
- **冲突只改配置和文档**：Coq代码(.v)冲突不擅改，标注后报告
- **JSON改完必验证**：`python3 -c "import json;json.load(open('文件'))"`
- **分站休眠正常**：不主动激活休眠分站，用户决定

**最佳手法**
