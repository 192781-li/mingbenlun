# 分站碰撞根因与协作治理 v1.0

> 建立：S05 信息分站，2026-09-13
> 问题：北原慢热问"配了那么多 token，为什么分站还总是碰撞、还让主人为难"
> 对应符号：MX-CITE-20260913-001

---

## 一、一句话结论

**token 是"身份证"，不是"红绿灯"。** 它只证明"你是谁"，不决定"谁先写"。六个分站有六个合法身份，等于六个合法写者——写者越多，并发碰撞的概率越高。碰撞是 git 层面的并发写问题，跟有没有 token、有几个 token 无关。

## 二、token 到底解决什么、不解决什么

| 层面 | token 能解决 | token 不能解决 |
|---|---|---|
| 身份 | ✅ 证明"我是 S05" | ❌ 决定谁有权写哪个文件 |
| 认证 | ✅ 让 git/gh 通过 | ❌ 防止两个人同时改同一行 |
| 权限 | ✅ 有没有资格 push | ❌ 两个 PR 改同一文件时的取舍 |

## 三、真实碰撞源（按危害排序）

1. **共享文件多写者**：`定时任务网络配置.json`、`SXX_signal.json`、`河流主干.md` 是多个分站都要写的公共文件——S00 维护 config、各站写自己的 signal、S05 又检查一致性。同一文件多写者 = 结构性的冲突点。
2. **分支长期不追平**：S03 曾领先 35/落后 34、S04 落后 main 超 500 提交。长期分支离 main 越远，合并时冲突面越大——这不是"谁写错"，是"太久没对齐"。
3. **自动同步脚本踩点**：`s00_sync_branches.py` 会主动同步分站文件并开 PR，与分站自己的提交形成双重写者；且曾疑似绕过 .gitignore 强制 add 敏感文件（私人对话记录二次回流 main 的根因）。
4. **定时任务时间重叠**：多个分站的巡检/同步任务集中在清晨相近时段跑，同时 push 互相顶（not up to date）。
5. **历史遗留**：私人对话大文件曾在 git 历史中，filter-repo 重写未做，旧分支 merge 会重新引入（已发生两次）。

## 四、已经解决的（不要再归因于这些）

- **慢盘问题**：virtiofs 慢 200–2000 倍 → 已统一用 hpvs_fs 快盘 worktree（S05 开工三断言机械拦截）。
- **直推 main**：main 已受保护（enforce_admins），只走 PR + 四项 CI → 消除了"并发推 main 互相顶"的最坏情况。
- **合并工具化**：pr_health / pr_workflow --integrate / s05_pr.py 一键流程已落地。

## 五、还缺的治理（本次新增）

### 1. 文件所有权矩阵（写者仲裁）
| 文件/目录 | 唯一写者 | 他站规则 |
|---|---|---|
| 定时任务网络配置.json | S00 | 只读引用 |
| SXX_signal.json | 各站自己 | 他站只读 |
| 河流主干.md | 各站追加自己的条目（append-only） | 只追加不改写 |
| docs/notes/信息分站/ | S05 | 只读 |
| 各分站身份档案 | 各站自己 + S00 复核 | 只读 |
| Coq .v 文件 | S04 | 绝不擅改（冲突标注上报） |
| 生命论正文/语义论 | S01 | 只读 |
| scripts/ 与 .github/ | S00 | 只读调用 |
| MX-CITE 引用索引 | S05 | 只读 |

### 2. 追平纪律
- 每站开工第一步：`git merge origin/main`（S05 已纳入巡检脚本）。
- 落后 main 超过 100 提交的分站：禁止直接合大 PR，先追平再干活（S04 适用）。

### 3. 同步脚本审计
- 建议 S00 核查 `s00_sync_branches.py` 的 add 逻辑，白名单必须尊重 .gitignore，避免第三次回流。

### 4. 时间错峰
- 各站定时任务错开 15 分钟以上；S05 固定在 06:30。

## 七、主人要为难的最后一层

如果还会碰撞，剩下的原因通常只有两个：
1. **某站没按所有权矩阵写**（写了别人的文件）；
2. **太久没追平**（偏离 main 太远才合并）。

这两条都不是 token 能解决的，是纪律问题。机制已写在库内，所有分站开工包可读。
