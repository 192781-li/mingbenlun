# 配置文件分区编辑机制 v1.0
> 设计时间：2026-09-02
> 设计者：S05 信息分站（TASK-003）
> 适用文件：docs/协作机制/明旭的记忆/定时任务网络配置.json
> 问题背景：多实例并发修改同一JSON导致冲突、cron_job_id不一致、版本号快速迭代

---

## 一、为什么需要分区编辑

### 当前问题
1. **并发冲突**：多个分站/实例同时修改 `定时任务网络配置.json`，导致 git merge conflict
2. **数据不一致**：配置里的 cron_job_id 与实际运行的任务 ID 不匹配
3. **责任不清**：不知道哪个字段是谁改的、为什么改
4. **版本混乱**：v1.3→v1.4→v1.5 快速迭代，但每次只改一小部分

### 分区原则
- **谁的分区谁负责**：每个分站只能修改自己的分区
- **公共区需协商**：修改公共区（task_queue、network_health）需要先 pull，标注修改原因
- **原子修改**：一次提交只改一个分区，不跨区批量修改
- **修改留痕**：每个分区有 `last_updated_by` 和 `last_updated_at` 字段

## 二、分区方案

### 2.1 分区定义

```
定时任务网络配置.json
├── meta（公共区，S00负责）
│   ├── version
│   ├── last_updated
│   ├── updated_by
│   └── description
│
├── branch_architecture（公共区，S00负责）
│   └── 分支架构信息
│
├── stations（分区，各分站负责自己的条目）
│   ├── S00（S00负责）
│   ├── S01（S01负责）
│   ├── S02（S02负责）
│   ├── S03（S03负责）
│   ├── S04（S04负责）
│   └── S05（S05负责）
│
├── task_queue（公共区，S00负责分配，各分站可认领）
│   └── 任务列表
│
├── growth_log（公共区，各分站可追加）
│   └── 成长日志
│
├── network_health（公共区，S05负责巡检更新）
│   └── 网络健康状态
│
├── cron_jobs（公共区，S00负责注册）
│   └── 定时任务注册表
│
└── stopped_jobs（公共区，S00负责）
    └── 已停止任务
```

### 2.2 各分区编辑权限

| 分区 | 负责分站 | 其他分站权限 | 修改频率 |
|---|---|---|---|
| meta | S00 | 只读 | 低（版本升级时） |
| branch_architecture | S00 | 只读 | 极低 |
| stations.SXX | SXX自己 | 只读 | 中（状态变化时） |
| task_queue | S00分配 | 可认领/更新状态 | 中 |
| growth_log | 各分站 | 可追加 | 高 |
| network_health | S05 | 只读 | 高（每日巡检） |
| cron_jobs | S00 | 可上报新任务 | 低 |
| stopped_jobs | S00 | 只读 | 极低 |

## 三、编辑流程SOP

### 3.1 修改自己的分区（如 S05 修改 stations.S05）

```bash
# 1. 先同步最新
git pull origin main

# 2. 修改自己的分区（用 python3 确保JSON格式正确）
python3 -c "
import json
d = json.load(open('docs/协作机制/明旭的记忆/定时任务网络配置.json'))
d['stations']['S05']['last_run'] = '2026-09-02 06:30:00'
d['stations']['S05']['last_output'] = '完成每日巡检'
json.dump(d, open('...', 'w'), ensure_ascii=False, indent=2)
"

# 3. 验证格式
python3 -c "import json; json.load(open('文件路径'))"

# 4. 提交（commit message 标注分区）
git commit -m "config[stations.S05]: 更新last_run和last_output"
git push origin s05-info
```

### 3.2 修改公共区（如 S05 更新 network_health）

```bash
# 1. 先同步（必须！）
git pull origin main

# 2. 修改公共区
# 3. 验证格式
# 4. 提交（commit message 标注公共区+修改原因）
git commit -m "config[network_health]: 每日巡检更新各分站状态"
```

### 3.3 认领任务（修改 task_queue）

```bash
# 1. 先同步
git pull origin main

# 2. 找到任务，修改 status 和 assigned_to
# 3. 验证格式
# 4. 提交
git commit -m "config[task_queue]: S05认领TASK-001，状态改为in_progress"
```

## 四、冲突解决规则

### 4.1 同分区冲突（两个实例改同一个分站的分区）
- **原则**：以最新的为准，但需要人工确认
- **操作**：保留两个版本的差异部分，用 `last_updated_at` 判断哪个更新
- **禁止**：直接覆盖对方的修改

### 4.2 跨分区冲突（不同分站改不同分区）
- **原则**：自动合并，互不影响
- **操作**：git merge 通常能自动解决，因为改的是不同的JSON key

### 4.3 meta 区冲突（version/last_updated）
- **原则**：以 S00 的版本为准
- **操作**：其他分站不要改 meta 区，只改自己的分区

## 五、JSON 结构增强建议

在每个分区增加元数据字段：

```json
{
  "stations": {
    "S05": {
      "_meta": {
        "last_updated_by": "S05",
        "last_updated_at": "2026-09-02 06:30:00",
        "edit_count": 42
      },
      "name": "信息分站",
      "status": "active",
      ...
    }
  }
}
```

这样可以追踪每个分区的修改历史，避免"不知道谁改的"。
