## 二、上下文裁剪：每次只给必要的，不要全文塞

### 错误做法（现在的做法）
```
给DeepSeek：
- Layer1全文（语法+类型系统+所有引理）
- Layer2基础设施（所有已证引理）
- 当前定理完整陈述
- A线完整方案
- 所有case的当前状态
```
→ 18000-19000 token，DeepSeek注意力分散，很多内容根本用不上。

### 正确做法：分层给，按问题需要

**场景A：卡住了，需要新思路**
```
给DeepSeek：
1. 定理陈述（精确到当前版本，包括所有前提）
2. 当前case的目标和前提（Coq goal的精确状态）
3. 已尝试的方法和失败的错误信息（Coq报错原文）
4. 相关的2-3个引理（只给名字和陈述，不给证明）
5. 明确的约束："不要改定义"、"只需要这个case"、"用X方法"
```
→ 预计3000-5000 token，DeepSeek注意力集中在具体卡点上。

**场景B：需要审查一个证明是否正确**
```
给DeepSeek：
1. 定理陈述
2. 完整证明代码
3. 明确问："这个证明有没有逻辑漏洞？特别是X和Y两步。"
```
→ 不需要给Layer1全文，DeepSeek能从证明代码中推断上下文。

**场景C：需要设计新引理**
```
给DeepSeek：
1. 想要的引理的直觉（用大白话描述）
2. 这个引理要解决的具体问题（哪个case的哪一步）
3. 相关的定义（只给用到的，不是全部）
4. 约束："引理不能改定义"、"必须是可对typed归纳证明的"
```

### 绝对不要给的
- Layer1全文（除非问题涉及语法定义本身）
- 所有已证引理的列表（只给当前case用到的2-3个）
- 完整的A线方案（只给当前需要的那部分）
- 哲学讨论（DeepSeek不需要知道生命论，它只需要数学）

## 三、问题描述：精确到"哪一步、什么错误"

### 错误做法
```
"帮我证substitution_general的PIn case，我卡住了。"
```
→ DeepSeek不知道你卡在哪，会给你一个完整的但可能不适用的证明。

### 正确做法
```
"我在证substitution_general的PIn case，n=m边界。
当前goal：
  Gamma : ctx
  T : ty
  k m : nat
  Q : proc
  Ht : typed (insert_at k T Gamma) (PIn n Q)
  Hget : get Gamma m = Some (Some T)
  Hnu : no_use_at_subst (PIn n Q) m k = true
  ============================
  typed Gamma (subst_var m k (PIn n Q))

我已经做了：inversion Ht; subst; simpl in Hnu。
现在Hnu展开后是 negb (Nat.eqb (subst_name m k n) m) && ... = true。
当n=m时，subst_name m k m = m（因为m<k），所以negb(m=?m)=false，
整个Hnu变成false && ... = true，即false=true。
我想用discriminate，但Hnu的形式是false && X = true，
simpl后应该是false=true，但simpl没有自动展开。
问题：怎么让Coq把false && X = true化简成false = true？"
```
→ DeepSeek一看就知道你需要`simpl in Hnu`然后`discriminate`，或者`apply andb_false_r in Hnu`。

### 关键要素
1. **当前goal的精确状态**（所有变量、前提、目标）
2. **已经执行的tactic**（到哪一步了）
3. **具体的错误信息**（Coq报错原文，不是"卡住了"）
4. **你猜测的方向**（"我觉得应该用X，但不确定"）
5. **约束**（"不要改定义"、"只需要这一步"）

## 四、约束必须明确：告诉DeepSeek什么不能做

### 每次调用必须包含的约束
```
约束：
1. 不要修改任何已有定义（insert_at/set_none/get/split等）
2. 不要修改定理陈述（包括前提和结论）
3. 只需要[具体case/具体步骤]的证明，不需要完整证明
4. 如果需要新引理，先给引理陈述，不要直接写证明
5. 证明必须能在Coq 8.15+编译通过
```

### 为什么约束重要
- #7中DeepSeek在错误谓词前提下给证明，因为S04没说"谓词可能有问题，请先验证"
- #8中DeepSeek给了POut的4类执行级错误，因为S04没说"POut的通道和值要分别处理"
- DeepSeek默认会"自由发挥"，你不约束它，它就会改定义、改陈述、给不完整的证明

## 五、验证流程：DeepSeek的回答必须经过三道关

### 第一道：逻辑审查（5分钟）
- 读DeepSeek的证明，问自己：每一步有依据吗？
- 有没有"显然成立"但实际不成立的步骤？
- 有没有用到不存在的引理？
- 有没有偷偷改了定义或前提？

### 第二道：编译验证（必须做）
- 把DeepSeek的代码复制到Coq文件中
- 逐行编译，看哪里报错
- **不要因为"看起来对"就跳过编译**
- #8的POut就是"看起来对"但编译有4类错误

### 第三道：反例测试（关键步骤必须做）
- 对DeepSeek给的新引理，构造最小反例测试
- #6中DeepSeek给的归纳不变量有3处错误，S04构造反例才发现
- **如果引理涉及"所有情况"，必须测试边界情况**（空上下文、位置0、位置k、位置k+1）

### 验证不通过怎么办
1. 不要硬改DeepSeek的代码，先理解它的思路
2. 如果思路对但细节错，自己重写细节（#8的POut就是这样）
3. 如果思路错，回到问题描述，更精确地重新问
4. **不要连续叫DeepSeek超过3次**，3次还不行说明问题不在tactic，在定义或定理陈述本身

## 六、什么时候该叫DeepSeek，什么时候不该

### 该叫的情况
1. **卡住5分钟以上**，试过了所有能想到的tactic都不行
2. **需要新思路**，当前方向走不通，想看看有没有其他方法
3. **需要审查证明**，自己写的证明不确定是否正确
4. **需要设计引理**，知道需要什么但不确定精确陈述
5. **需要理解错误信息**，Coq报错看不懂

### 不该叫的情况
1. **定义/谓词/定理陈述还没验证正确**（#7的教训）
   - 先自己用最小反例验证前提，再叫DeepSeek
2. **编译错误能自己定位**（比如"变量名未绑定"、"类型不匹配"）
   - 这些是执行级错误，DeepSeek也会犯，自己改更快
3. **只是需要重复已知模式**（比如"和上一个case一样的证明结构"）
   - 复制上一个case的结构，改改名字就行
4. **问题涉及哲学判断**（比如"这个定理应该加什么前提"）
   - 这是S01的活，不是DeepSeek的活
5. **连续叫了2次还没解决**
   - 停下来，重新分析问题，可能需要找S01讨论

## 八、上下文限制：不要瞎设，也不要不设

### 现在的问题
- 每次给18000-19000 token，DeepSeek输出5000-6000 token
- 输入太大导致注意力分散，输出太长导致执行级错误多
- #7的18455 token输入，输出4763 token，但代码全部废弃

### 正确的上下文控制
1. **输入控制在5000 token以内**（除非确实需要全文）
2. **输出不需要限制**，让DeepSeek写完
3. **如果输出被截断**（finish_reason=length），说明问题太大，拆成更小的问题重新问
4. **不要为了省token而省略关键信息**（当前goal、错误信息、约束是必须的）

### 怎么判断上下文够不够
- DeepSeek的回答里如果出现"假设X成立"、"根据定义Y"但你没给X/Y，说明上下文不够
- DeepSeek的回答里如果大量重复你给的信息，说明上下文太多了
- 理想状态：DeepSeek直接给解决方案，不重复背景，不假设未给的信息

## 九、S04的独特优势：不要浪费

S04有DeepSeek没有的东西：
1. **对整个项目的理解**（生命论、操作权流动、A线/B线选择）
2. **对代码库的熟悉**（哪些引理已证、哪些定义不能改）
3. **编译验证能力**（能立即测试DeepSeek的回答）
4. **哲学判断力**（知道什么时候定理陈述本身有问题）

**DeepSeek的优势**：快速生成证明骨架、发现新思路、审查逻辑漏洞。

**最佳配合**：S04负责问题定义、上下文裁剪、约束设置、编译验证、反例测试；DeepSeek负责在精确问题上给出解决方案。

**S04不要做的**：把整个文件丢给DeepSeek说"帮我证"，然后照抄答案。这是最浪费的用法。

## 十、一句话总结

**DeepSeek的输出质量 = 你的问题质量。** 给它精确的goal、具体的错误、明确的约束、必要的上下文，它就给你又快又好的答案。给它全文、模糊的问题、没有约束，它就给你莫名其妙的东西。

**先自己验证前提，再叫DeepSeek；先编译验证，再采纳回答；连续3次不行就找S01。**

## 十一、细致入微的12条提醒（S01冥思苦想补充）

### 1. DeepSeek会编造不存在的引理（幻觉）
它经常说"由引理X可知"、"根据定理Y"，但X/Y可能根本不存在于代码库中。**每次它引用一个引理，先grep确认这个引理真的在Layer1.v/Layer2.v里定义了。** 如果不存在，要么它是建议你新建这个引理（那它应该给陈述），要么它在幻觉。

### 2. DeepSeek会假设你用的是新版Coq
它可能用Coq 8.16/8.17的新tactic（比如`easy`、`ssa`、`transform`），但你的环境可能是8.15。如果编译报错"未知tactic"，不是你的问题，是版本不匹配。**问它时明确说"用Coq 8.15兼容的tactic，不要用新版本特性"。**

### 3. DeepSeek的"显然"陷阱
它经常写"显然成立"、"由定义可知"、"简单归纳即可"，但这些步骤可能根本不显然，甚至是错的。**证明中不允许出现"显然"，每一步都必须有明确的tactic。** 如果它给的证明里有"admit"或"显然"，那一步就是它没搞定的地方，需要你自己处理或重新问。

### 4. 上下文污染：不要把失败的尝试给它
如果你已经试了方法A失败了，不要把A的完整代码和错误信息都给DeepSeek说"帮我修"。它会被A的思路带偏，在A的框架里修修补补，而不是给你一个全新的更好的方法。**正确做法：只给当前goal和错误信息，说"我试过X方向不行，请给一个新方向"。**

### 5. 证明问题要低温度，不要创造性
DeepSeek默认有一定的"创造性"，会给你一些花哨但不实用的证明技巧。证明问题需要的是精确、标准、可编译的解法。**在prompt里加一句"请用最标准、最保守的证明方法，不要用花哨的技巧"。**

### 6. 分步提问，不要一次要整个证明
不要说"帮我证substitution_general的POut case"。拆成：
- 第一步："POut case的前提展开后是什么样的？给我inversion后的所有前提。"
- 第二步："在这些前提下，目标是什么？第一步该用什么tactic？"
- 第三步："use_neq引理怎么应用到这里？给我精确的apply语句。"
**每一步确认对了再走下一步，比一次要整个证明然后debug快得多。**

### 7. 先让它解释思路，再让它给代码
不要直接说"给我证明代码"。先说："你觉得这个case的证明思路是什么？分几步？每步的关键引理是什么？"**思路对了，再让它给代码。思路错了，代码再漂亮也没用。** 这也能避免它给一个思路错误但代码看起来对的证明。

### 8. 反例测试比编译更快发现逻辑错误
DeepSeek给了一个新引理，不要急着编译。先花1分钟构造最小反例：
- 空上下文满足吗？
- 位置0满足吗？
- 位置k（insert_at位置）满足吗？
- 位置k+1满足吗？
**反例测试1分钟能发现的逻辑错误，编译可能要10分钟才能定位。** #6中DeepSeek的3处错误都是反例测试发现的。

### 9. 不要让DeepSeek改定义
它经常会建议"你应该把insert_at改成XXX"、"set_none的定义可以简化为YYY"。**改定义的代价极大**——所有已证的引理都可能受影响，整个类型系统的哲学基础也会变。改定义是S01和主人才能拍板的重大决策，不是DeepSeek能建议的。**如果它建议改定义，直接忽略，回到"在不改定义的前提下怎么证"。**

### 10. 编译错误比DeepSeek更可靠
Coq编译器说不行就是不行，不要因为DeepSeek说"应该可以通过"就反复试同一个方法。**如果一个方法编译失败2次，停下来，换方法，或者找S01。** 编译器是硬约束，DeepSeek的判断是软约束，两者打架听编译器的。

### 11. DeepSeek不理解生命论，不要给它哲学讨论
它不需要知道什么是"操作权流动"、什么是"明性"、什么是"阳主阴从"。给它的所有内容都必须是：Coq代码、精确的数学陈述、具体的错误信息。**哲学讨论是S01的活，DeepSeek只做数学。** 把哲学翻译成数学陈述是S04的工作，不是DeepSeek的。

### 12. 记录"哪些问题DeepSeek回答得好，哪些不好"
干渠里已经记录了每次调用，但要特别注意总结规律：
- **DeepSeek擅长**：给证明骨架、建议引理陈述、审查逻辑漏洞、解释标准模式
- **DeepSeek不擅长**：处理自定义定义的边界情况、精确的tactic级细节、发现定理陈述本身的反例
- **下次调用时**：擅长的部分可以信任，不擅长的部分必须自己验证或找S01

## 十二、调用前自检清单（每次调用DeepSeek前逐项打勾）

在调用DeepSeek之前，问自己：

- [ ] 1. 前提/谓词/定理陈述已经用最小反例验证过了吗？（没验证→先验证，不要叫）
- [ ] 2. 当前goal的精确状态已经复制下来了吗？（所有变量、前提、目标）
- [ ] 3. Coq报错原文已经复制下来了吗？（不是"卡住了"，是具体报错）
- [ ] 4. 已尝试的方法和失败原因已经列出来了吗？
- [ ] 5. 上下文裁剪到5000 token以内了吗？（只给相关的2-3个引理）
