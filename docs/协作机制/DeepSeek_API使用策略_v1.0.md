# DeepSeek API 使用策略 v1.0

> 建立时间：2026-08-29
> 目的：充分、高效、精准地使用DeepSeek API，避免只用最低档模型
> 原则：四规定性检验——边界生成性（能做什么）、内生目的性（为什么用）、操作再生性（怎么稳定产出）、环境互动性（与其他工具配合）

---

## 一、模型选择（三档）

| 模型 | 适用场景 | 特点 | 成本 |
|------|---------|------|------|
| `deepseek-v4-flash` | 简单任务、快速响应、批量处理 | 无思考链，速度快 | 低 |
| `deepseek-v4-pro` | 复杂任务、深度推理、哲学分析 | 有思考链，质量高 | 中 |
| `deepseek-v4-flash-vision-exp` | 图片理解、截图分析、图表识别 | 支持图片输入 | 中 |

**选择判据**：
- 需要"想清楚再答"的 → pro
- 只需要"快速处理"的 → flash
- 需要"看图片"的 → vision

---

## 二、思考强度控制（两档）

| 参数 | 适用场景 |
|------|---------|
| `reasoning_effort: "high"` | 一般复杂任务（默认） |
| `reasoning_effort: "max"` | 特别复杂的任务（深度哲学分析、多文档综合、理论突破） |

**开关**：`thinking: {"type": "enabled/disabled"}`

**注意**：思考模式下不支持temperature、top_p等参数。

## 三、核心功能使用场景

### 3.1 JSON Output（结构化输出）
- **何时用**：需要生成表格、分类、元数据、可解析的结构化结果
- **怎么用**：`response_format: {"type": "json_object"}`，prompt中必须含"json"字样并给出样例
- **注意**：有概率返回空content，需重试

### 3.2 Files API（文件复用）
- **何时用**：同一张图片需要在多个请求中复用；图片超过32MiB
- **怎么用**：先上传获取`file_id`，再用`{"type": "file", "file_id": "..."}`引用
- **限制**：单文件最大64MiB，单用户最多10000个文件，25GiB空间

### 3.3 图像理解
- **三种传入方式**：Base64内联、外部URL、Files API file_id
- **细节级别**：`low`（512×512，省token）/ `high`/`original`（保留原图）
- **Token上限**：每张图片最多384 token（自动缩放到约800×800）

### 3.4 工具调用（Function Calling）
- **何时用**：需要多步推理+操作（如先查数据再分析）
- **怎么用**：思考模式下传入`tools`参数，模型自动决定调用
- **注意**：有工具调用的轮次，后续必须回传`reasoning_content`

### 3.5 上下文硬盘缓存（前缀缓存）——工程实现规范
- **本质**：DeepSeek自动缓存请求的**前缀**。从第一个token开始连续一致的部分命中，**一旦某处变化，其后再相同也不命中**。无需显式开启。
- **命中效果**：命中部分按缓存价计费（约为正常输入价的1/10）。
- **铁律：固定内容前置，变化内容后置。** prompt必须按以下顺序拼接：
  1. 【固定层】角色、任务说明、扫描维度、输出格式、严谨度要求——每个请求逐字相同，抽成模块级常量，多进程并行也能共享这份前缀缓存
  2. 【追加增长层】累积上下文/历史摘要——只追加不重写，相邻请求的这层前缀重叠，可命中（用滑动窗口时窗口尽量稳定，避免每次从头切掉太多）
  3. 【变化层】本次编号、时间戳等
  4. 【独占层】本次独有的原始材料（如逐块原文），放最后
- **反例（2026-08-29史官分析踩坑，命中率0-6.6%）**：把"第X块、时间{dr}"写在prompt第一段、固定说明之前，导致前缀在块号处断裂，后面2000字本可命中的固定维度/格式全部未命中。这是"文档里写了缓存、代码里没落实"的闭环短路。
- **验证方法**：本地构造相邻两个请求，用代码算最长公共前缀长度，确认变化内容都被推到公共前缀之后；上线后看开放平台"输入（命中缓存）/输入（未命中缓存）"比值。
- **多进程并行**：所有并行worker必须共用同一份固定层常量字符串（逐字一致），才能跨进程命中同一前缀。

## 四、生命论项目的具体应用策略

### 4.1 对话记录深度分析
- **模型**：`deepseek-v4-pro`
- **思考强度**：`max`
- **功能**：JSON Output（输出结构化的演变脉络、概念演化、同源对话识别）
- **场景**：16个对话的概念演变分析、理论突破点识别、时间线重建

### 4.2 哲学文本处理
- **模型**：`deepseek-v4-pro`
- **思考强度**：`max`
- **功能**：普通对话（输出深度哲学分析）
- **场景**：硬核哲学文本的解读、概念辨析、理论综合

### 4.3 图片/截图分析
- **模型**：`deepseek-v4-flash-vision-exp`
- **思考强度**：`high`
- **功能**：图像理解（Base64或URL传入）
- **场景**：用户上传的截图、聊天记录截图、图表分析

### 4.4 批量结构映射
- **模型**：`deepseek-v4-flash`
- **思考强度**：`high`（或关闭）
- **功能**：JSON Output
- **场景**：文件分类、目录映射、重复文件识别

### 4.5 代码/形式化分析
- **模型**：`deepseek-v4-pro`
- **思考强度**：`max`
- **功能**：工具调用（如先读文件再分析）
- **场景**：Coq证明分析、代码审查、形式化验证

## 五、成本控制策略

1. **简单任务用flash**：不要什么都用pro
2. **不需要思考时关闭thinking**：纯格式转换、简单摘要不需要思考链
3. **使用上下文缓存**：重复分析同一批文档时，先缓存上下文
4. **合理设置max_tokens**：不要给太大的max_tokens，避免浪费
5. **批量处理**：把多个小任务合并成一个请求，减少调用次数
6. **先flash后pro**：先用flash做初步筛选，再用pro深入分析有价值的部分

## 六、与其他工具的配合

| 任务 | 首选工具 | DeepSeek角色 |
|------|---------|-------------|
| 文件操作 | Bash/Read/Edit | 不参与 |
| 简单搜索 | general_search | 不参与 |
| 深度哲学分析 | DeepSeek pro | 主力 |
| 图片理解 | DeepSeek vision | 主力 |
| 结构化输出 | DeepSeek + JSON | 主力 |
| 多文档综合 | DeepSeek pro + 上下文缓存 | 主力 |
| 代码执行 | Bash/Python | DeepSeek只做分析 |

---

## 七、之前犯的错误（教训）

1. **用错模型名**：用了`deepseek-chat`/`deepseek-reasoner`，应该用`deepseek-v4-flash`/`deepseek-v4-pro`
2. **只用最低档**：一直用flash，没有用pro
3. **没调思考强度**：没有显式设置`reasoning_effort`
4. **没用视觉模型**：一直用Read工具看图片，应该用DeepSeek vision
5. **没用JSON Output**：需要结构化输出时没有用
6. **没用上下文缓存**：重复分析时没有缓存
