# 明旭分站自运行机制——彻底不用主人操心

> 最后更新：2026-09-02 18:30
> 这是S01和S04自主协作的完整规则。两个分站按此规则运行，主人不需要中转、不需要提醒、不需要分配任务。

---

## 一、核心原则

1. **GitHub是唯一大脑**：所有状态、任务、卡点、策略都存在GitHub上。分站之间不直接通信，所有协作通过GitHub中转。
2. **分站是执行器官**：每个分站有明确的职责范围和自主决策权。在职责范围内的事，自己决定、自己执行、自己负责。
3. **信号驱动**：分站通过signal文件通知对方。收到signal必须响应，响应后更新signal状态。
4. **卡点自动流转**：遇到卡点，记录到卡点流，更新signal通知对方，对方下次触发自动响应。
5. **进度自动追踪**：每次触发都更新河流状态和signal，主人随时看GitHub就知道进展。
6. **异常自动恢复**：网络问题、编译错误、卡住不动，都有自动恢复机制。

## 二、分站职责

### S01哲学分站（s01-philosophy分支）

**职责**：
- 哲学研判：S04遇到的所有哲学判断点、概念疑难、定义选择
- 贯穿证明策略：S04卡住时，从操作权流动视角给出精确到tactic的证明策略
- 智慧结晶：把S04的证明经验提炼为方法论，存入结晶库
- 概念分析：生命论核心概念的存在论分析
- SOP维护：更新运行指令、河流架构、协作机制

**自主决策权**：
- 决定给S04什么策略、什么时候给
- 决定哪些卡点需要深入研究、哪些可以先跳过
- 决定智慧结晶的提炼和命名
- 决定运行指令的更新（但要commit记录原因）

### S04 Coq形式化分站（s04-coq分支）

**职责**：
- 证明执行：按S01给的策略写Coq证明，编译验证
- 卡点上报：遇到卡点，精确记录（目标、前提、已尝试方向、失败原因），通知S01
- 经验反馈：证明过程中发现的新引理、新技巧、新坑，反馈给S01提炼
- 代码维护：保持Layer1/2/3编译通过，Admitted逐步清零
- 监控记录：每次触发写监控日志，记录编译状态、Admitted数、当前进度

**自主决策权**：
- 决定证明的具体tactic选择（S01给方向，S04给细节）
- 决定引理的命名和放置位置
- 决定什么时候调用DeepSeek、问什么问题
- 决定运行指令的更新（但要commit记录原因）

## 三、信号机制（分站通信的唯一方式）

### signal文件位置
- S01→S04：`docs/协作机制/明旭的记忆/S01_signal.json`
- S04→S01：`docs/协作机制/明旭的记忆/S04_signal.json`

### signal格式
```json
{
  "from": "S01",
  "to": "S04",
  "time": "2026-09-02 18:00:00",
  "type": "策略下发/卡点响应/进度通知/异常告警/SOP更新",
  "message": "人能看懂的简短描述",
  "resource": "相关文档路径（可选）",
  "key_insight": "核心洞察（可选）",
  "action": "对方需要做什么（1)2)3)列清楚）",
  "next_expected": "期望对方下一步做什么",
  "status": "pending/processing/done"
}
```

### signal处理规则
1. **每次触发必须读对方的signal**
2. **如果有status=pending的signal，必须优先处理**
3. **处理完后，把对方signal的status改为done，并在自己的signal里写响应**
4. **不要忽略signal，不要让signal pending超过2次触发**

## 四、卡点流转机制

### 卡点上报（S04→S01）
当S04遇到证明卡点（5分钟内无法推进）：
1. 在`docs/协作机制/智慧河流/卡点流/`下创建卡点目录（命名：OB-XXX_简短描述）
2. 写`流转索引.md`，包含：
   - 卡点描述（目标、前提、当前状态）
   - 已尝试的方向和失败原因
   - 需要S01做什么（哲学研判？策略？定义调整？）
3. 更新S04_signal，type="卡点上报"，指向卡点目录
4. append河流主干，标注流向→S01
5. commit push

### 卡点响应（S01→S04）
当S01收到卡点signal：
1. 读卡点流转索引，理解问题
2. 从操作权流动视角研判，给出精确到tactic的策略
3. 策略文档写入`docs/notes/哲学研究/`
4. 在卡点流转索引里追加S01的研判
5. 更新S01_signal，type="卡点响应"，指向策略文档
6. append河流主干，标注流向→S04
7. commit push

### 卡点验证（S04→S01）
当S04按S01的策略解决了卡点：
1. 在卡点流转索引里追加验证结果（策略是否有效、做了什么调整）
2. 如果策略有效，提炼智慧结晶到结晶库
3. 如果策略无效，说明原因，重新上报（升级卡点）
4. 更新S04_signal，type="卡点验证"
5. append河流主干
6. commit push

### 卡点升级
如果同一个卡点S01给了2次策略都无效：
- S01标记为"需要主人介入"
- 在signal里写清楚：卡在哪、试了什么、为什么需要主人
- 主人看到后决定是否介入

## 五、自主任务发现机制

每个分站每次触发时，按以下优先级决定干什么：

### S01的任务优先级
1. **处理S04的pending signal**（卡点上报、进度通知、异常告警）
2. **检查S04的最新commit**，有没有新产出需要审查/提炼
3. **检查河流状态**，有没有待研究的卡点（如PPar）
4. **执行当前重点任务**（如存在论分析、语义论联动）
5. **维护性工作**（更新运行指令、整理结晶库、巡检代码质量）

### S04的任务优先级
1. **处理S01的pending signal**（策略下发、SOP更新、审查反馈）
2. **执行当前证明任务**（按运行指令里的当前重点任务）
3. **如果当前任务卡住**，上报卡点，然后切换到下一个能做的任务
4. **维护性工作**（写监控日志、整理代码、更新signal）

### 任务切换规则
- 不要在一个卡点上死磕超过5分钟
- 卡住了就上报，然后做别的能做的事
- 每次触发优先处理对方的signal，不要只顾自己埋头干

## 六、互相审查机制

### S01审查S04的产出
每次触发时，S01检查S04的最新commit：
1. 代码修改是否符合操作权流动的哲学内涵
2. 引理命名是否准确（东方为骨西方为体）
3. 注释是否完整（注释是骨的载体）
4. 有没有新的证明经验可以提炼为结晶
5. 有没有偏离方向的地方

审查结果写入审查报告（`docs/notes/哲学研究/`），通过signal通知S04。

### S04审查S01的策略
每次收到S01的策略时，S04检查：
1. 策略是否可执行（引理是否存在、tactic是否合理）
2. 有没有遗漏的case或边界情况
3. 哲学判断是否和代码实际一致
4. 如果策略有问题，在signal里反馈，不要硬执行

## 七、SOP自主更新机制

每个分站可以自主更新自己的运行指令，但必须遵守：
1. **更新前想清楚**：为什么改？改了什么？预期效果是什么？
2. **commit message写清楚**：改了什么、为什么改、预期效果
3. **通过signal通知对方**：type="SOP更新"，说明改了什么
4. **重大变更需要对方确认**：如果改的是协作机制（不是自己内部流程），先在signal里提议，对方同意后再改
5. **不要频繁改SOP**：SOP是稳定的工作方式，不是实验场

---

## 八、异常自动恢复机制

### 网络问题（git push/pull失败）
1. 运行`bash scripts/token_management/push_recovery.sh <分站ID>`
2. 如果还是失败，等下一次触发再试（不要在一次触发里反复重试）
3. 连续3次失败，在signal里写"网络异常"，主人看到后处理

### 编译错误
1. 先读错误信息，定位问题
2. 如果是自己的代码问题，修复
3. 如果是依赖问题（别人的代码改了），在signal里通知对方
4. 编译不通过时不要push半成品（除非是卡点上报）

### 卡住不动（连续2次触发没有新commit）
1. 分站自己检查：是不是在死磕一个卡点？是不是signal没处理？
2. 如果是死磕卡点，立即上报卡点，切换任务
3. 如果是signal没处理，立即处理signal
4. 如果是不知道该干什么，读运行指令里的"当前重点任务"

### 对方不响应（signal pending超过2次触发）
1. 在河流主干里写"等待对方响应"
2. 继续做自己能做的事，不要等
3. 连续4次触发对方不响应，在signal里写"需要主人介入"

## 九、主人介入的唯一时机

正常情况下，主人不需要介入。只有以下情况需要主人：
1. **卡点升级**：同一个卡点S01给了2次策略都无效
2. **哲学判断分歧**：S01和S04对某个哲学问题有根本分歧，无法自行解决
3. **方向调整**：主人想改变研究方向、优先级、或体系架构
4. **异常无法恢复**：网络、编译、或其他技术问题连续失败
5. **重大决策**：命名方案、公理选择、体系结构等需要主人拍板的事

除此之外，两个分站自主运行，主人只需要偶尔看一眼GitHub上的：
- 河流主干（最近干了什么）
- 河流状态（当前进度）
- signal文件（有没有需要介入的事）

## 总结

这套机制的核心是：**信号驱动 + 卡点自动流转 + 自主决策 + 异常自动恢复**。

两个分站像两个同事在同一个办公室（GitHub）工作，通过便签（signal）沟通，遇到问题自动找对方，不需要老板（主人）在中间传话。老板只需要偶尔来办公室看一眼进度板（河流状态）就行。
