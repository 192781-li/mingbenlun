## 怎么用这个地图（30秒上手）

1. **冷启动**（第一次激活/长时间未运行）：读你分站的"冷启动路径"
2. **日常触发**：读"核心必读"（3篇以内）+ 当前任务标注的【必读】文档
3. **卡住了**：查"反模式索引"——你踩的坑可能别人踩过了
4. **找东西**：查"关键词检索表"——按问题找文档

## 四、反模式索引：别再走的死路

> 这是最有价值的部分——不是告诉你"该做什么"，是告诉你"别做什么"。每个反模式都有真实的代价记录。

| 反模式 | 表现 | 代价 | 正确做法 | 来源 |
|--------|------|------|---------|------|
| 🚫 换方法绕路 | 证明证不出来就换一种方法，换了五种 | 5轮DeepSeek，$0.1+，一周时间 | 小本质递归：先深挖定义，定义错了什么方法都不行 | subst_var bug |
| 🚫 一次写大证明 | 让DeepSeek一次写完整证明 | 输出被截断（16384 tokens），190+多余引理 | 分小块，每次2-3个case，编译验证 | v5/v7失败 |
| 🚫 对typed归纳 | 对类型关系归纳而不是对proc结构归纳 | 650行证明，小错误层出不穷 | 对proc结构归纳，subst_var定义就是对proc递归的 | 最初650行证明 |
| 🚫 造黑话/广义引理 | 为了优雅引入ctx_insert等复杂抽象 | Gamma=[]时不成立，多了要证的东西 | 明本学术：直接面对卡点，用最简单的工具 | ctx_insert失败 |
| 🚫 假设太窄 | 归纳假设固定k=0 | PIn/PRes里k变成1后不够用 | 反者道之动：一般化假设，k任意 | substitution_general |
| 🚫 依赖DeepSeek找方向 | 卡住了就叫DeepSeek，它说什么是什么 | 被它带偏，hallucinate出编译不过的证明 | 四步走（小本质→操作还原→明本→反者）都试过了才叫 | 多次失败 |
| 🚫 跨对话创建一次性任务 | 在S01对话里创建任务"唤醒"S04 | 任务在S01对话里触发，骂声一片 | 每个分站的定时任务只能在自己对话里创建 | ID 10945694191618 |
| 🚫 埋头干不抬头 | 有commit但不更新状态机、不写报告 | S01不知道S04在干什么，协作断裂 | 每干完一步更新状态机+写报告，有哲学问题立即抛 | 协作协议第六章 |

## 九、阅读确认机制（v2.1新增）

> 光有地图不够，要确认分站真的读了。每个分站维护自己的"阅读确认清单"，每次触发时逐项检查。

### 9.1 S04阅读确认清单（每次定时任务触发时执行）

S04每次触发，在开始干活前，必须逐项确认以下内容（在运行状态机的"阅读确认日志"里记录）：

```
[ ] 1. 我读了证明智慧手册的四步法（小本质→操作还原→明本学术→反者道之动）
[ ] 2. 我读了当前任务的精确骨架（如果有）
[ ] 3. 我读了反模式索引，确认当前做法不在8条死路里
[ ] 4. 我读了教训库最近3条
[ ] 5. 卡住时，我先按四步法走了一遍，才叫DeepSeek
```

确认方式：不是口头说"读了"，是在运行状态机里记录"本次触发读了X文档，关键要点是Y"。

### 9.2 没读的后果

如果S04触发后没有完成阅读确认就开始干活，且结果是失败的（编译不过、证明被截断、走了反模式），则：
1. 在反模式索引里新增一条
2. 在教训库里记录
3. 下一轮触发时必须先补读再干活

### 9.3 智慧注入验证（S01/S05负责）

每次S01产出重要文档后，验证：
- [ ] 智慧地图已更新
- [ ] 相关任务描述已注入【必读】链接
- [ ] 如果是S04长期必读，已写入S04阅读确认清单
- [ ] 24小时内S04的运行状态机里有阅读记录

三项都打勾，才算智慧真正注入成功。
