# doubao-book-writer 使用指南（生命论项目专用）

> 性质：非虚构长文档工作台skill，用于系统性写作和质检长文档。
> 诞生时间：2026-08-29
> 来源：doubao-book-writer skill
> 版本：v1.0

---

## 一、这个skill是干什么的

专门用来系统性地写和质检**非虚构长文档**（手册、白皮书、报告、哲学著作、资料型书稿等），不写小说剧本。

核心是一条 `make` 控制的交付链：

```
prepare（准备材料+需求清单）→ write（写正文）→ quality（质检）→ deliver（交付）
```

---

## 二、关键硬规则（必须遵守）

1. **只信磁盘文件和脚本结果**，不凭对话记忆判断阶段完成。
2. 正文真源只能是Markdown。
3. **动笔前先写需求清单**（目标、读者、篇幅、素材边界），缺时先问最少必要问题。
4. 长稿必须有大纲和章节台账（各章目标字数之和=全书目标）。
5. 局部编辑只改授权范围；未授权章节不借质检、润色或扩写名义重写。
6. 改写、扩写、组装、精修前先备份原稿。
7. **扩写要增加论点、证据、案例或结构信息**，不用复述和同义改写凑字数。
8. 每写完一批正文就运行质检。失败先修当前稿件，不继续铺新章。
9. **质检失败只改正文和资料，不改脚本、不改阈值、不手写报告冒充通过。**
10. 最终只转述脚本给出的 PASS / BLOCKED / DRAFT_ONLY。

## 三、在生命论项目中的应用场景

### 3.1 每周全本篇章深化写作（主要应用）

"每周全本篇章深化写作"任务执行时，套用 book-writer 的流程：

1. **prepare**：选中篇章后，先写需求清单——
   - 这章要解决什么问题（深化目标）
   - 目标字数/篇幅
   - 素材边界（哪些已有内容保留、哪些需要补充、哪些不能碰）
   - 读者定位（全本读者是谁）
2. **write**：按照需求清单深化写作，补充论点/证据/案例/结构信息，不用同义改写凑字数
3. **quality**：写完后质检——
   - 论点是否完整（有没有半途而废的论证）
   - 证据是否支撑（每个结论有没有理由和证据）
   - 结构是否清晰（小节之间有没有逻辑连接）
   - 去AI味（有没有套话、有没有喊口号、有没有生存体验支撑）
   - 严谨度标注（定理/命题/猜想/启发式是否区分）
4. 只信磁盘文件结果，不凭对话记忆说"完成了"

### 3.2 长文档组装（未来应用）

当生命论全本需要从模块化文件组装为完整书稿时，用 book-writer 的 assemble 流程：
- 先写大纲和章节台账
- 再按顺序组装各模块
- 最后跑全本质检

### 3.3 去AI味精修（辅助应用）

当某篇文章AI味太重时，用 book-writer 的 revision-quality 子流程做精修：
- 先备份原稿
- 再逐段检查（有没有套话、有没有缺乏生存体验、有没有大词拜物教）
- 最后质检确认

## 四、与现有机制的关系

| 现有机制 | book-writer补什么 |
|----------|-------------------|
| 模块化系统（生命论_模块化/） | 需求清单、章节台账的结构化管理 |
| quality_gate.py（交叉引用/定理检查） | 更通用的正文质检（论点完整性、证据支撑、去AI味） |
| 核心巡检（全局扫描） | 单篇/单章的深度写作和精修流程 |
| 全本篇章深化写作（每周任务） | 用book-writer的prepare→write→quality流程执行 |

**不重复的部分**：book-writer不做交叉引用检查、不做定理注册表检查、不做全局结构扫描——这些是quality_gate.py和核心巡检的事。book-writer专注于**单篇/单章的写作质量**。

## 五、使用命令参考

```bash
# 完整交付链
make WORKDIR=<书稿目录>

# 分步执行
make prepare WORKDIR=<书稿目录>   # 准备材料+需求清单
make write   WORKDIR=<书稿目录>   # 写正文
make quality WORKDIR=<书稿目录>   # 质检
make deliver WORKDIR=<书稿目录>   # 交付
make status  WORKDIR=<书稿目录>   # 查看状态
```

用户明确不要飞书时加 `SKIP_LARK=1`。

## 六、交付口径

- **PASS**：正文检查通过，终稿已生成
- **BLOCKED**：准备、写作或交付被脚本拦住，回复卡点和下一步
- **DRAFT_ONLY**：有正文，但质检或交付未过。只能称未验收草稿

最终回复不粘贴内部JSON、不展示门禁日志、不把对话生成内容当成交付物。给用户文件路径或真实阻塞原因。

---

*记住：这个skill的核心精神是"只信磁盘和脚本，不凭记忆和感觉"——和生命论的"怀疑止于践演"是同构的。*
