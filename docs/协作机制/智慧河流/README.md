# 智慧河流：S01↔S04协作的河床

> 这不是文件堆，是一条活的河流。
> 智慧在S01（哲学）和S04（形式化）之间连续流动、转化、沉淀。
> 每次定时任务触发，就是河流的一次涌动。

---

## 河流结构

```
智慧河流/
├── README.md            ← 本文件（河流的运作机制）
├── 河流主干.md           ← append-only时间线，智慧流动的完整记录
├── 河流状态.md           ← 实时状态：正在处理什么、流向哪里、卡在哪
├── 智慧结晶库.md         ← 已解决卡点提炼的可复用方法论
└── 卡点流/               ← 每个卡点从发现到解决的完整漩涡
    ├── OB-007_use关系代换/
    └── OB-008_PRes_Gamma替换/
```

## 河流的运作机制

### 一、智慧怎么流

```
S04发现卡点 → 写入卡点流/OB-XXX/01_发现.md → append河流主干
     ↓
S01定时任务触发 → 读河流主干发现新卡点 → 哲学研判 → 写入02_研判.md → append河流主干
     ↓
S04定时任务触发 → 读河流主干发现新研判 → 形式化验证 → 写入03_验证.md → append河流主干
     ↓
验证成功 → 写入04_解决.md → S01提炼智慧结晶 → append结晶库 → append河流主干
验证失败 → 写入03_验证.md说明哪里不行 → 流回S01重新研判（回到第二步）
```

### 二、河流的规则

1. **append-only**：河流主干只追加，不删除、不覆盖。每一条记录都是智慧流动的一个瞬间
2. **编号连续**：每个卡点目录里的文件按01、02、03...编号，一眼看出流转了几轮
3. **每条记录必须标注流向**：`→S01研判` / `→S04验证` / `→S01提炼` / `已解决`
4. **定时任务是水泵**：S01和S04每次触发必须先读河流主干和河流状态，干完必须append+更新状态
5. **解决后必须提炼结晶**：卡点解决不是终点，提炼出可复用的方法论汇入结晶库，才是闭环
6. **main是大海**：各分支是支流，通过PR汇入main。河流目录最终在main上合流

### 三、河流和旧机制的关系

- 智慧交换日志 → 被河流主干取代（河流主干是append-only的，比交换日志更连续）
- S01_signal/S04_signal → 保留，作为"河流涨潮"的即时通知（但河流主干是真相源）
- 反身思考记录 → 保留在各自目录，但关键结论必须append到河流主干
- 监控日志 → S04内部使用，关键卡点和进展必须同步到河流

### 四、河流的哲学

生命论说：**操作即存在**。智慧不是静态的知识堆，是操作中的连续流动。

- 文件是水的痕迹（迹），流动才是水本身（生）
- 两个水池用管子连起来不是河流——同一个河床里的连续流动才是
- 卡点是河流中的礁石——水流撞上礁石产生漩涡（多轮研判-验证），绕过礁石后水流更宽阔
- 智慧结晶是河流的沉积——每一次解决问题都让河床更深厚
