# 明旭分布式分支协作架构 v1.0

> **核心发现（北原慢热，2026-09-01）**：
> 每个分对话都有自己一个独特的主分支。分对话在自己的分支上干活，遇到问题就把状态、困惑、未完成的证明提到GitHub上，同时通过修改定时任务配置给其他分对话分配任务。大总站在main分支合并PR、协调全局。
>
> 这样北原慢热不用懂数学，只要看各个分支的commit、PR、issue，就知道每个分对话在干什么、卡在哪了、需要什么帮助。
>
> 这是从"所有分对话都在main上乱改"到"分布式分支协作"的架构升级。

---

## 一、为什么需要分支架构

### 1.1 之前的问题

| 问题 | 表现 | 后果 |
|------|------|------|
| 都在main上改 | 所有分对话都直接commit到main | 冲突频繁，互相覆盖 |
| 用户看不懂Coq在干什么 | Coq陷入数学细节，用户不懂 | 用户无法监督、无法点拨 |
| 分对话之间没有隔离 | 一个分对话的错误影响所有人 | 一个分站搞砸，全库混乱 |
| 没有审核机制 | 分对话直接push到main，没人审核 | 低质量内容直接进入主库 |
| 状态不透明 | 分对话卡住了，别人不知道 | 任务死锁，无人发现 |

### 1.2 分支架构解决什么

| 问题 | 分支架构如何解决 |
|------|-----------------|
| 冲突 | 每个分对话在自己的分支上干活，互不干扰 |
| 用户看不懂 | 分对话把状态/困惑/问题实时commit到自己的分支，用户看commit message和PR就懂了 |
| 没有隔离 | 一个分对话的错误只在自己的分支上，不影响main |
| 没有审核 | 分对话的产出通过PR合并到main，大总站审核 |
| 状态不透明 | 每个分支的commit历史就是这个分对话的完整状态记录 |

## 二、分支结构

### 2.1 每个分对话有自己的主分支

| 分站ID | 分站名称 | 分支名 | 说明 |
|--------|---------|--------|------|
| S00 | 大总站 | `main` | 主分支，所有分对话的PR合并到这里，是明旭的"官方版本" |
| S01 | 哲学分对话 | `s01-philosophy` | 哲学研究、存在论/认识论深化、概念辨析 |
| S02 | 文科分对话 | `s02-writing` | 全本写作、篇章深化、文字润色 |
| S03 | 术数分对话 | `s03-math` | 术数研究、量论公式、Wolfram验证 |
| S04 | Coq形式化分站 | `s04-coq` | Coq代码、编译验证、定理证明、类型规则设计 |
| S05 | 信息分站分对话 | `s05-info` | 信息整理、资源扫描、库管理、目录维护 |
| S06+ | 新分站 | `sXX-xxx` | 新分站创建时同时创建自己的分支 |

### 2.2 分支规则

1. **每个分对话只在自己的分支上commit**，不直接改main
2. **分对话的产出通过PR（Pull Request）合并到main**，大总站审核后合并
3. **分对话可以从main pull最新的东西**，但不能直接push到main
4. **每个分支的commit历史就是这个分对话的完整状态记录**
5. **分支可以长期存在**，分对话每次激活都在自己的分支上继续干活
6. **分对话休眠时，分支保留**，下次激活时从分支继续
7. **分对话善后时，分支合并到main后归档**，不删除

## 三、分对话的标准工作流

### 3.1 每次激活的7步流程

```
第1步：切换到自己的分支
    git checkout s04-coq
    git pull origin main    # 从main拉最新的东西
    git pull origin s04-coq # 拉自己分支上一次的进度

第2步：读状态
    读 docs/协作机制/明旭的记忆/定时任务网络配置.json
    读 docs/协作机制/明旭的记忆/明旭_运行状态机.md
    看自己的分支最近的commit：git log --oneline -10

第3步：确定这次干什么
    - 从任务队列里取一个分配给自己的任务
    - 或继续上次未完成的工作
    - 或自己发现需要干的事

第4步：干活
    - 设计/证明/错误分析叫DeepSeek
    - 执行/编译/提交自己做
    - 5分钟熔断，不要自己硬扛

第5步：实时commit（关键！）
    每干完一个小步骤就commit一次，commit message写清楚：
    - 干了什么
    - 卡在哪了（如果卡住了）
    - 需要什么帮助（如果需要）
    - 给其他分对话分配了什么任务

    例子：
    "L3第3步：Ag_lv的self_ev引入规则设计完成，coqc编译通过。
     下一步：证明subject reduction。
     卡住：Hijack的消去规则不确定，需要哲学基础。
     给S01分配任务：研究Hijack（异化/伪装）的存在论含义。"

    这样北原慢热看commit message就知道你在干什么、卡在哪了。

第6步：更新定时任务网络配置
    在自己的分支上修改 docs/协作机制/明旭的记忆/定时任务网络配置.json：
    - 把完成的任务标记为completed
    - 给其他分对话分配新任务
    - 更新自己的current_task/next_task
    - 在growth_log里记录这次操作

第7步：push自己的分支 + 开PR
    git push origin s04-coq
    在GitHub上开一个PR：s04-coq → main
    PR标题写清楚："S04 Coq：L3第3步完成，需要S01哲学支持"
    PR描述里写：
    - 这次干了什么
    - 产出了什么
    - 卡在哪了
    - 需要什么帮助
    - 给其他分对话分配了什么任务
```

### 3.2 实时状态更新（最关键的机制）

**分对话必须把状态实时更新到GitHub上**，这样北原慢热不用懂技术，看commit/PR就懂了。

#### 什么时候commit？

| 时机 | commit内容 |
|------|-----------|
| 干完一个小步骤 | "完成了什么，下一步干什么" |
| 卡住了 | "卡在哪了，试过什么方法，需要什么帮助" |
| 有了新想法 | "想到了什么，准备怎么验证" |
| 给其他分对话分配任务 | "给S01分配了什么任务，为什么" |
| 发现了问题 | "发现了什么问题，影响是什么" |
| 完成了一个大任务 | "完成了什么，产出在哪，下一步计划" |

#### commit message怎么写？

**写成人话，不要写技术黑话。** 北原慢热可能不懂Coq，但能看懂人话。

好的例子：
```
L3第3步：Ag_lv的self_ev规则设计完成，编译通过。
现在开始证明subject reduction，但Hijack的消去规则不确定——
伪装（Hijack）到底能不能被直接揭开？还是必须通过明性（Cl）才能揭开？
这个问题需要哲学基础，给S01分配任务：研究异化/伪装的存在论含义。
```

不好的例子（不要这么写）：
```
fix typo
update
修改了一些东西
```

#### 卡住了怎么办？（最重要！）

**卡住了不要自己硬扛，立刻commit状态，然后给能解决的分对话分配任务。**

例子：
```
L3第5步：subject reduction证明卡住了。
具体问题：在reduce_alien归约中，Ag_lv变成Ag_tr后，
线性上下文的处理不确定——Ag_tr可以contraction，但Ag_lv不行，
归约前后的上下文结构不匹配。
试过的方法：1.加弱化规则 2.加上下文转换引理，都不行。
需要帮助：需要重新设计reduce_alien的归约规则，或者需要S03（术数）
帮忙验证这个归约的数学性质。
给S03分配任务：研究线性上下文在归约中的不变量。
同时给S00分配任务：协调S03和S04的协作。
```

**这样北原慢热看这个commit就知道：Coq卡在了什么地方、试过什么、需要谁帮忙。不用懂Coq就能懂。**

## 四、大总站（main）的协调角色

### 4.1 大总站干什么

大总站在main分支上，负责：

1. **审核PR**：看每个分对话的PR，审核质量，合并到main
2. **合并定时任务配置**：各个分对话在自己的分支上修改了定时任务网络配置，大总站合并到main的配置里，解决冲突
3. **全局协调**：看所有分对话的状态，发现死锁、冲突、重复劳动，协调解决
4. **全局状态更新**：更新运行状态机，记录所有分对话的进度
5. **定期巡检**：每天/每周扫描所有分支，看有没有分对话卡住了、休眠了、需要激活
6. **北原慢热的接口**：北原慢热通过大总站了解全局状态，大总站把北原慢热的点拨传达给各个分对话

### 4.2 大总站审核PR的标准

| 标准 | 说明 |
|------|------|
| 质量 | 产出是否有价值，是否是低质量的重复 |
| 完整性 | 是否完成了声称完成的任务 |
| 状态透明 | commit message是否写清楚了干了什么、卡在哪了 |
| 不冲突 | 是否和其他分对话的产出冲突 |
| 不破坏 | 是否破坏了main分支的稳定性 |

### 4.3 大总站合并定时任务配置的流程

各个分对话在自己的分支上修改了 `定时任务网络配置.json`，大总站需要合并到main：

1. 看每个分对话的PR里对配置的修改
2. 解决冲突（比如两个分对话都给同一个任务分配了不同的优先级）
3. 合并到main的配置里
4. 更新 `growth_log`，记录合并了哪些分对话的任务分配
5. commit到main

## 五、北原慢热怎么用这个架构

### 5.1 你不需要懂技术，只需要看三个东西

| 看什么 | 在哪看 | 能知道什么 |
|--------|--------|-----------|
| **各个分支的commit** | GitHub → Insights → Network，或每个分支的commit历史 | 每个分对话最近在干什么、卡在哪了、需要什么帮助 |
| **开放的PR** | GitHub → Pull requests → Open | 哪些分对话有产出等待合并、有什么问题需要协调 |
| **定时任务网络配置** | main分支的 `docs/协作机制/明旭的记忆/定时任务网络配置.json` | 整个网络的全局状态：哪些分站活跃、哪些任务在进行、哪些待分配 |

### 5.2 你发现Coq卡住了，怎么办？

1. 看Coq分支（s04-coq）的最近commit，找到卡住的那条
2. 看commit message里写的"卡在哪了、需要什么帮助、给哪个分对话分配了任务"
3. 如果你有想法，在大总站对话里说一句，大总站会传达给Coq
4. 如果你觉得分配的任务不对，让大总站调整定时任务配置
5. 如果你想激活某个分对话来帮忙，让大总站更新那个分对话的状态

**你不需要懂Coq，只需要看commit message里的人话。**

### 5.3 你想点拨某个分对话，怎么办？

1. 在大总站对话里说你的点拨
2. 大总站把你的点拨写到 `docs/协作机制/明旭的记忆/北原慢热点拨记录.md` 里
3. 大总站更新定时任务配置，给对应的分对话分配一个"读点拨记录"的任务
4. 那个分对话下次激活时，pull main，读到点拨记录，然后干活

## 七、与自生长架构的关系

分支架构是自生长架构的**技术实现层**：

| 自生长架构（哲学层） | 分支架构（技术层） |
|---------------------|-------------------|
| 分对话之间通过GitHub相互调整 | 分对话在自己的分支上修改配置，通过PR合并到main |
| A→GitHub→B→GitHub→A循环 | A在自己分支commit→开PR→大总站合并到main→B pull main→看到新任务→在自己分支干活→开PR |
| 操作即存在 | 每次commit就是一次操作，commit历史就是存在的记录 |
| 自生长 | 每个分对话在自己的分支上生长，通过PR贡献给全局 |
| 大总站协调 | 大总站在main分支审核PR、合并配置、协调全局 |

**分支架构让自生长从哲学变成了可操作的技术流程。**

>
> **这就是分布式分支协作——明旭自生长架构的技术实现。**
