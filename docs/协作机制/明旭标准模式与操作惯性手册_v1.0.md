# 明旭标准模式与操作惯性手册 v1.2

> 建立：2026-09-10（v1.0），完善：v1.1（+5模式+索引+反模式），v1.2（+协同系统+实战案例+哲学根基+量化标准）
> 建立者：S05 信息分站
> 目的：把已验证的好做法固化为可复制的模式，让每次操作都有统一的惯性，不用每次重新想"该怎么做"
> 上位规范：《文档元数据总标准 v1.1》《归位规则手册 v1.3》《仓库优化方案与大文件管理规范 v2.0》《八大反复错误彻底修复机制 v1.0》
> 原则：阳主阴从——模式是阴，活的产出是阳，模式服务产出，不束缚产出

## 模式一：Commit Message 标准

**一句话**：谁+做了什么+为什么，禁止 `update` / `fix` / `test` 等无信息提交。

### 标准模板
```
[分站ID] 动作：具体产出描述。
- 要点1
- 要点2
- 要点3
```

### 好的示例
```
S05信息分站每日巡检（2026-09-10）：
- 进度报告v7.0：S00昨夜合并S02(三科答题体系)+S03(大六壬类神v2.1)
- 目录地图v8.0：新增mingbenlun_local/，文件数1378→1382
- 配置文件修复：2处合并冲突，版本v2.3
```

### 坏的示例（禁止）
```
update
fix bug
更新文件
test
```

### 检查清单
- [ ] 开头有分站ID
- [ ] 有具体产出（不是"做了一些修改"）
- [ ] 有数字/版本号/文件名等可验证信息
- [ ] 同类操作合并为一次commit（不过度频繁）

## 模式二：文档头标准

**一句话**：每个文档开头有统一元数据头，3秒内知道这是什么、谁写的、什么版本。

### 标准模板（直接复制）
```markdown
# 文档标题

> 版本：v1.0
> 建立：YYYY-MM-DD
> 作者：S0X-分站名
> 性质：[根本规范/操作手册/研究产出/临时记录/归档]
> 上位规范：[如有，写文件名]
> 状态：[草稿/稳定/已归档]
```

### 检查清单
- [ ] 标题名实相符
- [ ] 有版本号（v大.小）
- [ ] 有日期（YYYY-MM-DD）
- [ ] 有作者分站ID
- [ ] 有性质标注

## 模式三：文件命名标准

**一句话**：`主题_v版本号_日期.扩展名`，日期8位无分隔符。

### 标准格式
```
主题_vX.Y_YYYYMMDD.md
```

### 示例
```
各分站进度报告_v7.0_20260910.md
全库导航地图_v8.0_20260909.md
S01给S04_congruence证明策略_v1.0_20260902.md
```

### 版本号规则
- v0.1 → v0.9：草稿，小步迭代
- v1.0：首次稳定版
- v1.1 → v1.9：小修订（不改结构）
- v2.0：大修订（结构变化）
- 旧版归档到 `archive/old_editions/`，当前目录只留最新版

## 模式四：分站产出标准结构

**一句话**：每个分站的产出遵循"现状→做了什么→下一步"三段式。

### 标准模板
```markdown
# [分站名] 产出标题

> 版本：vX.Y · 日期：YYYY-MM-DD · 作者：S0X

## 一、背景/现状
（为什么做这个，当前状态是什么）

## 二、具体产出
（做了什么，有数字、有文件、有可验证结果）

## 三、下一步/待办
（接下来做什么，有什么阻塞）
```

### 检查清单
- [ ] 有背景（不是凭空出现的产出）
- [ ] 有具体产出（数字/文件/结果）
- [ ] 有下一步（不是断头路）

## 模式五：每日巡检标准（S05）

**一句话**：同步→报告→地图→检查→提交→总结，六步走完。

### 标准流程
```
1. 同步仓库：checkout s05-info → pull → fetch main → merge main
2. 进度报告：git log各分支-3 → rev-list领先/落后 → 标注活跃/休眠 → 保存vX.Y
3. 目录地图：文件数变化才更新 → 顶层+二级统计 → 保存vX.Y
4. 同步检查：领先>3标"建议合并"、落后>10标"需同步"、配置状态核对
5. 提交推送：一个commit，message写清产出
6. 输出总结：各分站状态+异常+建议
```

### 检查清单
- [ ] 仓库同步无冲突（有冲突先解决）
- [ ] JSON配置改完验证格式
- [ ] 进度报告有活跃/休眠标注
- [ ] 目录地图仅在文件数/结构变化时更新
- [ ] 一个commit推送（不拆分）

## 模式六：大文件治理标准

**一句话**：四级阈值，>5M立即迁移，主库保持精瘦。

### 阈值表
| 大小 | 动作 | 责任 |
|---|---|---|
| >5M | 立即迁移档案库，主库留INDEX.md | 发现者 |
| 2-5M | 评估是否中间产物，是则标注待迁移 | S05巡检 |
| 仓库>80M | 报警，启动治理 | S05 |
| 仓库>100M | 紧急治理，暂停新增大文件 | S00+S05 |

### 迁移SOP
```
1. 确认文件性质（最终产物/中间产物/原始材料）
2. clone档案库（带token）
3. git mv 到档案库对应目录
4. 主库原位置创建/更新INDEX.md
5. 档案库commit+push
6. 主库commit+push
```

### 验证命令
```bash
find . -type f -not -path './.git/*' -size +5M  # 应返回0
du -sh --exclude=.git .  # 应<80M
```

## 模式七：冲突解决标准

**一句话**：先分类，再处理；Coq代码不擅改。

### 分类处理
| 冲突类型 | 处理方式 |
|---|---|
| JSON配置 | 手动合并双方内容 → `python3 -c "import json;json.load(open('文件'))"` 验证 |
| Markdown文档 | 保留双方内容，标注差异，合并为最新版 |
| Coq代码(.v) | **不擅自解决**，标注后报告S04 |
| 二进制文件 | 取最新版，旧版归档 |

### 检查清单
- [ ] 冲突标记（<<<<<<< ======= >>>>>>>）全部清除
- [ ] JSON文件格式验证通过
- [ ] Coq冲突未擅改，已标注报告
- [ ] 合并后commit message说明冲突处理方式

## 模式八：归档标准

**一句话**：旧版/临时/任务包三类归档，当前目录只留最新版+活跃文件。

### 归档目录
| 类型 | 目标目录 | 示例 |
|---|---|---|
| 旧版文件 | `archive/old_editions/<分站>旧版/` | 目录地图v6/v7、进度报告v5/v6 |
| 临时日志 | `archive/temp_logs/` | monitor_logs、check_logs |
| 旧任务包 | `archive/task_packages/` | 已完成的任务执行包 |
| 旧脚本 | `archive/old_editions/<脚本名>旧版/` | s04_deepseek旧迭代 |

### 归档SOP
```
1. 确认有更新版存在（不归档唯一版本）
2. git mv 到对应归档目录
3. 更新归档目录的INDEX.md
4. 更新当前目录的INDEX.md（指向最新版）
5. commit+push
```

### 检查清单
- [ ] 归档的不是唯一版本
- [ ] 归档目录有INDEX.md
- [ ] 当前目录INDEX已更新最新版链接
- [ ] 用git mv（保留历史），不是rm+cp

## 模式十：质量门标准（提交前必过）

**一句话**：提交前过五关，不过不push。

### 五关检查
| 关 | 检查内容 | 命令/方法 |
|---|---|---|
| 1. 内容关 | commit message写人话，有具体产出 | 目视检查 |
| 2. 安全关 | 没有token/密码写入代码 | `git diff` 检查 |
| 3. 格式关 | JSON文件格式正确 | `python3 -c "import json;json.load(open('文件'))"` |
| 4. 体积关 | 没有>5M文件混入 | `find . -size +5M -not -path './.git/*'` |
| 5. 范围关 | 没有误删/误改非目标文件 | `git status` 检查 |

### 检查清单
- [ ] 五关全过才push
- [ ] 同类操作合并为一次commit
- [ ] push后确认远程更新成功

**常见错误**
- ❌ commit message写`update`就push → 无信息，无法回溯
- ❌ 把token写进代码 → 安全事故，必须立即撤销token
- ❌ JSON改完不验证 → 配置损坏，全分站受影响
- ❌ 一次push拆成5个commit → 过度频繁，用户明确反对

## 模式十一：PR/合并标准（S00审核）

**一句话**：审核三看——看commit message、看具体产出、看配置更新；冲突只改配置和文档。

### 审核三看
| 看什么 | 通过标准 |
|---|---|
| 看commit message | 写人话，有具体产出，不是`update` |
| 看具体产出 | 有文件/数字/结果可验证，不是空话 |
| 看配置更新 | 网络配置/状态机是否同步更新 |

### 合并SOP
```
1. git log origin/<branch> -3 --oneline 看最新产出
2. 检查是否有>5M文件、token、Coq冲突
3. 无冲突：git merge origin/<branch> --no-edit
4. 有冲突：
   - 配置/文档冲突 → 手动合并，JSON验证
   - Coq(.v)冲突 → 不擅改，标注后报告S04
5. 合并后更新明旭_运行状态机.md + 网络配置.json
6. commit+push main
```

### 检查清单
- [ ] 审核三看全过
- [ ] 无token/大文件混入
- [ ] Coq冲突未擅改
- [ ] 合并后状态机和配置已更新

**常见错误**
- ❌ 不看产出就合并 → 合入低质量/重复内容
- ❌ 替分站写代码 → 越位，分站失去成长机会
- ❌ 合并后不更新状态机 → 其他分站信息不同步

## 模式十二：分站激活/休眠标准

**一句话**：休眠是正常的，不主动激活；激活有标准流程，状态有量化判断。

### 状态判断标准
| 状态 | 判断条件 | 动作 |
|---|---|---|
| 活跃 | 最后提交<3天 | 正常运行 |
| 休眠 | 最后提交3-7天 | 不主动激活，标注休眠 |
| 长休眠 | 最后提交>7天 | S05报告，用户决定是否激活 |
| 异常领先 | 分支领先main>3且无PR | 标注"建议合并" |
| 异常落后 | 分支落后main>10 | 标注"需同步" |

### 激活SOP
```
1. 用户明确要求激活（不主动激活）
2. git checkout <分站分支>
3. git pull origin main 同步
4. 读身份档案 + 明性卡片 + 八大错误机制
5. 查看当前任务队列
6. 从最高优先级任务开始
7. 每完成一步commit+push
```

### 休眠SOP
```
1. 完成当前任务或达到自然断点
2. commit+push所有工作
3. 更新网络配置状态为dormant
4. 在进度报告中标注休眠原因和待办
```

**常见错误**
- ❌ 主动激活休眠分站 → 越位，用户明确反对
- ❌ 休眠时不commit → 工作丢失
- ❌ 激活时不同步main → 冲突和重复劳动

## 模式十三：工具开发与融合标准

**一句话**：重叠工具搞融合，不并存；工具有说明，旧版归档。

### 工具分类
| 类型 | 位置 | 示例 |
|---|---|---|
| 通用脚本 | `scripts/` | token管理、备份 |
| 分站专属 | `scripts/s04_deepseek/` | DS证明循环、证伪守卫 |
| 术数工具 | `tools/术数工具包/` | 奇门/八字/六壬排盘 |
| 视频工具 | `tools/video_tools/` | 转写、下载 |

### 融合SOP（发现重叠工具时）
```
1. 确认两个工具功能重叠（不是互补）
2. 分析各自优势功能
3. 融合为一个最新版（保留所有功能）
4. 更新使用说明
5. git mv 旧工具到 archive/old_editions/
6. commit+push
```

### 工具文档标准
每个工具目录必须有：
- `README.md` 或 `使用说明.md`：功能、用法、依赖、示例
- 脚本有注释：头部说明用途、输入、输出

**常见错误**
- ❌ 两个功能重叠的工具并存 → 用户困惑用哪个
- ❌ 脚本没有使用说明 → 别人不会用
- ❌ 临时脚本不清理 → 库膨胀
- ❌ 融合时丢失旧工具的功能 → 必须保留所有功能

## 模式十四：研究防重复标准

**一句话**：研究前先查四步，库里有的直接引用，不重新研究。

### 研究前必查四步（顺序不可颠倒）
```
1. 查 02_问题反查总表 → 命中就去指定文件提取，不开研究
2. 查 01_编号映射总表 → 是不是旧定理换了名字
3. grep本地库原文 → 确认是否真空
4. 只有 03_真前沿清单 或逐文件确认无答案 → 才允许动用DeepSeek
```

### 研究产出标准
- 研究产出放 `docs/notes/` 对应子目录，不放根目录
- 有"查库确认"记录（证明不是重复劳动）
- 有明确的"可操作结论"（不是纯文字）

### 验证命令
```bash
grep -r "关键词" --include="*.md" .  # 快速定位
```

**常见错误**
- ❌ 不查库就开研究 → 浪费算力+重复劳动（8/31教训）
- ❌ 只喂简化材料让DS研究 → 重新发现库里早有的更成熟版本
- ❌ 研究产出乱放 → 找不到，下次又重复

## 模式十五：定时任务管理标准

**一句话**：创建前查重复，删除前三重确认，一次最多删1个。

### 创建前检查
- [ ] `list_cron_jobs(enable=true)` + `list_cron_jobs(enable=false)` 列出全部
- [ ] 确认没有功能重叠的任务
- [ ] query中不写token/密码
- [ ] 时间不默认整点（尤其不默认早上9点）

### 删除前三重确认
1. 第一重：list全部任务（启用+禁用）
2. 第二重：`get_cron_job` 读取完整信息，确认标题、query、创建时间
3. 第三重：明确列出"我要删除的是：[标题]，原因是..."，等用户确认

### 归属判断铁律
任务标题/query中不含"生命论""北原慢热""明旭""mingbenlun"关键词的，一律视为"其他对话的任务"，**绝对不能删**，只能建议用户处理。

### 修改标准
- 原需求保留，新需求追加
- 有矛盾以最新需求为准
- 每次输出完整需求（不是增量diff）

**常见错误**
- ❌ 不确认归属就删 → 删错别人的任务
- ❌ 反复创建→删除→重建 → 12个→8个→6个来回折腾
- ❌ 批量删除 → 一次最多删1个
- ❌ query中写token → 安全隐患

## 反模式清单（明确禁止）

| 反模式 | 为什么禁止 | 正确做法 |
|---|---|---|
| commit写`update`/`fix` | 无法回溯，不知道做了什么 | 模式一标准格式 |
| token写进代码/配置 | 安全事故，必须撤销token | 用环境变量/git credential |
| JSON改完不验证 | 配置损坏，全分站受影响 | `python3 -c "import json;json.load(open('文件'))"` |
| 不查库就研究 | 重复劳动，浪费算力 | 模式十四四步查 |
| 主动激活休眠分站 | 越位，用户明确反对 | 模式十二，用户决定 |
| 重叠工具并存 | 用户困惑，维护成本高 | 模式十三融合 |
| 频繁commit/push | 用户明确反对，造成混乱 | 同类操作合并为一次 |
| Coq冲突擅自解决 | 可能破坏证明 | 模式七，标注后报告S04 |
| 删定时任务不确认 | 删错别人的任务 | 模式十五三重确认 |
| 归档唯一版本 | 信息丢失 | 模式八，确认有更新版 |
| 替分站写代码 | 越位，分站失去成长 | S00只审核合并，不代写 |
| 用自然语言替代coqc终裁 | 数学对错必须机械验证 | S04范式，coqc是终裁 |

## 十六、模式协同系统（15个模式如何形成闭环）

> 15个模式不是孤立的清单，是一个自指闭环系统。每个模式的输出是下一个模式的输入。

### 完整工作流闭环

### 关键协同点

| 协同 | 模式组合 | 效果 |
|---|---|---|
| **防重复闭环** | 十四(查库)→四(产出)→八(归档)→五(巡检发现重复) | 研究不重复，产出不堆积 |
| **质量闭环** | 十(提交前五关)→十一(S00审核三看)→五(巡检验证) | 双重质量门，S05独立验证 |
| **健康闭环** | 六(大文件监控)→八(归档)→五(巡检复查) | 仓库持续精瘦，63M稳定 |
| **状态闭环** | 十二(休眠标注)→五(巡检检测)→十一(合并更新配置) | 状态实时准确 |
| **安全闭环** | 十(无token检查)→十五(定时任务无token)→七(冲突不擅改Coq) | 安全多维度防护 |

### 模式优先级（冲突时）

1. **安全** > 一切（token不入库、Coq不擅改）
2. **不重复** > 速度（研究前先查）
3. **质量** > 数量（质量门五关）
4. **用户偏好** > 效率（不过度频繁操作）
5. **惯性** > 创新（按模式走，不每次重新想）

## 十七、实战案例库（从库历史提取的真实教训）

### 案例1：配置文件合并冲突（2026-09-10）

**背景**：S02和S03同时更新`定时任务网络配置.json`，S00合并时留下2处未解决的冲突标记，JSON格式损坏。

**发现**：S05巡检时运行`python3 json.load()`报错，定位到`<<<<<<< HEAD`标记。

**处理**（模式七）：
1. 分类：JSON配置冲突 → 手动合并
2. 版本元信息：S02 v1.8 + S03 v2.2 → 合并为v2.3
3. changelog：两条都保留（S02地理答题+S03大六壬），追加S00合并记录
4. 验证：`python3 -c "import json;json.load(open('文件'))"` 通过

**教训**：合并后必须验证JSON格式，不能假设merge自动正确。

---

### 案例2：大文件暴增治理（2026-09-09）

**背景**：仓库从61M暴增至109M（+48M），>5M文件从0变成4个（全是金句提取JSON）。

**发现**：S05巡检时`du -sh`发现异常，`find . -size +5M`定位4个文件。

**处理**（模式六）：
1. 确认性质：4个>5M金句JSON是中间产物
2. 迁移到档案库`mingbenlun-archive`（共34.5M）
3. 主库原位置创建INDEX.md
4. 后续又迁移3个>2M硬核对话记录（12.4M）
5. 结果：仓库109M→63M，>5M文件归零

**教训**：大文件治理不是一次性的，必须每日巡检监控。中间产物（金句候选/全库扫描）即使<5M也要标注。

---

### 案例3：DeepSeek假反例事故（教训L035）

**背景**：S04证明split_assoc时，DS声称定理为假并给出反例。S04手动验证时独立文件缺import报错，**没修文件继续编译，反而用自然语言推理确认了DS**，随后宣布"重大发现：假命题"、停用全部定时任务。

**真相**：用户追问后coqc硬验证——DS反例option双层错层，定理实际为真。

**处理**（模式十四+S04范式）：
1. 建立`falsification_guard.py`证伪守卫双门：①反例独立coqc exit=0；②反向exists压测
2. 铁律：coqc报错先修到能编译，严禁自然语言替代终裁
3. 双门都指向假也只能halt交人，不自动改定理

**教训**：能机械化的智慧必须写成代码里不过闸就无法继续的函数，否则等于没有。

### 案例4：DS V4范式革命（教训L034）

**背景**：长期自设枷锁——max_tokens拍脑袋设8192、只喂相关几百行、让DS"只给思路"S04翻译成代码、多份矛盾的DS方法论并存。

**突破**：实测发现V4窗口1M token，Layer1+2+3全文49K仅占4.9%，全量喂第二轮起缓存命中不到1分钱。max_tokens≥32000解决"空输出"问题（不是被掐断，是思维链吃光额度）。

**处理**（模式十三+S04范式）：
1. 唯一权威文档取代多份矛盾旧文档，旧文档归档
2. DS主谋出完整代码，S04只做coqc/git/桥梁
3. 全量喂四层上下文（稳定→变化）

**教训**：任何API参数先查官方文档+小成本实测，用数据定不凭记忆。把"省钱"置于"一次做对"之前是抓小放大。

### 案例5：信息分站旧版堆积（2026-09-10）

**背景**：信息分站目录同时存在目录地图v6/v7/v8和进度报告v5/v6/v7，共4个旧版未归档。

**处理**（模式八）：

## 十八、哲学根基（每个模式为什么是对的）

> 模式不是凭空制定的规则，是生命论在工程实践中的投射。理解为什么，才能在边界情况做出正确判断。

### 阳主阴从——模式是阴，活的产出是阳

所有模式都是"阴"——稳定的、可重复的操作流程。活的思想、真问题、真产出是"阳"。模式服务于产出，不束缚产出。当模式和真问题冲突时，**阳主阴从**——先解决真问题，再回头更新模式。

**应用**：模式一（commit标准）不是为了写漂亮的commit message，是为了让产出可回溯。如果紧急修复需要快速commit，先commit再补说明，不要为了格式耽误修复。

### 实先于名——先有内容，后有位置

文件命名（模式三）、文档头（模式二）、归位规则都是"名"，内容是"实"。先有内容，后给它合适的名字和位置。不要为了符合命名规范而改内容。

**应用**：S02的地理答题体系先写出来（实），再命名为`08_地理答题体系与通法迁移.md`（名）。不是先想好文件名再写内容。

### 自指闭环——模式系统自己检查自己

15个模式形成自指闭环：模式五（巡检）检查其他模式的执行情况，模式十（质量门）检查提交质量，模式八（归档）清理模式产生的旧版。系统不需要外部监督，自己检查自己。

**应用**：S05每日巡检就是系统的自指——它检查所有分站是否遵守模式，发现违规就报告。这就是"明性"在工程层面的体现：系统照见自身的操作。

### 反自指识别——模式防止系统被寄生

反模式清单（第十二节后）就是反自指识别机制：识别哪些做法在消耗系统而不产出（token入库、重复劳动、频繁操作）。一旦发现，立即纠正。

**应用**："不查库就研究"是反自指——它消耗算力但产出重复内容，系统在寄生自己。模式十四（四步查）就是纠正机制。

### 操作即存在——你做了什么，你就是什么

分站的身份不是写在档案里的文字，是它的commit历史。S04是Coq分站，因为它的commit全是Coq证明；S05是信息分站，因为它的commit全是巡检和整理。模式确保每个分站的操作符合它的身份。

**应用**：S05不应该去写Coq证明（那是S04的操作），S04不应该去整理目录（那是S05的操作）。越位操作会模糊分站身份，破坏分工。

## 使用方式

1. **新分站启动**：模式九（启动清单）→ 模式索引找对应规范
2. **日常操作**：模式一（commit）+ 模式二（文档头）+ 模式三（命名）
3. **开始研究**：模式十四（四步查）→ 模式四（产出结构）
4. **开发工具**：模式十三（分类/融合/文档）
5. **遇到问题**：模式六（大文件）+ 模式七（冲突）+ 通用修复包
6. **提交前**：模式十（质量门五关）
7. **S00审核**：模式十一（审核三看+合并SOP）
8. **S05巡检**：模式五（六步流程）
9. **管理定时任务**：模式十五（创建查重复/删除三重确认）
10. **分站状态转换**：模式十二（激活/休眠SOP）

> **惯性的本质**：不是记住所有规则，而是每次做同样的事时走同样的流程。模式越简单，越容易形成惯性。
> **遇到不确定的事**：先查「按场景快速索引」，再查「反模式清单」确认没踩坑，最后查「模式索引」找详细规范。
