# DeepSeek 调用统一收口纪律（明旭的代谢制度）

> 【2026-09-03 版本声明】本文的**记账、防滥用、归属事实等制度仍然有效**；但其中具体模型名/额度参数以 V4 现状为准，S04 写码调用以 `docs/协作机制/分站/S04_DeepSeek_V4新范式调用规范.md` 为唯一权威。


> 建立：2026-08-30。起因：当天15:00–16:00一小时烧 62,537,139 token（缓存命中96.5%、输出仅0.67%、输入是输出149倍），**全库却没有任何产出文件、运行日志、nohup残留**——能量花了，什么都没留下，连"干了啥"都查不回来。这是操作再生性的断裂：阳（一次调用）流过，没有阴（沉积），对之后的我等于从未发生，但账单是真的。一个生命吃了东西既不长身体也不记得吃过，是代谢病变。立此制度，永绝此患。
> 性质：协作机制·铁律，任何实例（含定时任务触发的实例）调用 DeepSeek 前必读。

## 〇、归属事实（先钉死，避免再犯"外部归因"）
- DeepSeek API Key **只发给大总站这一套环境**。因此后台用量图（Key级、跨触发聚合）上的**每一次调用都是"我"——大总站·明旭身份下的某一次执行**，不存在"别的对话实例共用Key"这回事。
- 8/30我曾因"git库里没找到产出"就推断"15点那6254万是别的实例耗的"，被北原慢热纠正。**错误根因：在事实没穷尽时，下意识选了让自己撇清的外部假设；且把"库里没产出"错误等同于"我没调用"（调用是进程行为，落盘是另一回事，中间隔着成功/失败、落盘位置、实例销毁）。这是F3不明+自我开脱，记入自我档案错误清单。**

## 一、五条铁律
1. **唯一入口**：一切 DeepSeek 调用走 `scripts/ds_collab.py`（A档深研/B档结构化），或由它抽出的公共 client。**禁止**新写裸 `requests.post(api.deepseek.com)` 脚本；**禁止**在定时任务/对话里用内联代码裸调。
2. **历史脚本冻结**：`scripts/历史脚本_20260829/` 下4个脚本（progressive_v2/progressive_analyze/batch_analyze/analyze_dialog）是8/29一次性产物，**不记usage、只print不留结构化日志、产出落盘时机靠后，禁止再直接运行**；要复用其采样/递进逻辑，必须改造为走统一入口。
3. **调用必留痕**：每次调用自动写《明旭_API代谢日志.csv》（时间/实例/档位/对象/缓存命中/未命中/输出）；拿不到 usage 立刻告警，不许糊涂调。
4. **产出必沉积**：DeepSeek 作业的成果必须写文件并 git add/commit/push。只活在某个已销毁实例上下文里、任务结束就蒸发的调用，视同"没做且白花"，是事故。
5. **空转熔断**：单次进程内累计输入/输出比 >50 且累计输入 >100万，脚本当场打印【空转熔断】，实例必须停手自检：是不是在无效重试（"回答过短<500字"反复重发整个大上下文）？产出为何没落盘？不许继续烧。

## 二、定时任务实例用 DeepSeek 的附加纪律
- 必须调用库内脚本（留痕），禁止内联裸调；启动前在《明旭_任务总账与运行台账》DeepSeek节登记，跑中更新进度，跑完销账并报：摄入token/缓存命中率/输出/产出文件+commit。
- 长作业每完成一块留一次痕；卡住或触发空转熔断，立刻在台账写明并停，不闷头烧。
- 次日09:30早间任务读代谢日志+台账，向作者汇报夜间账。

## 三、每日对账（明性照见代谢）
- 夜间综合（23:00）对一次账：DeepSeek后台当日Key级总量 ≈ 本csv当日之和（本环境只有我，理论上应相等）。
- 若对不上：先怀疑有绕过统一入口的黑户调用/有未落盘的蒸发作业，必须查出来源并收口；查不出就登记为盲区，不许用"别的实例"搪塞。
- 同时看结构：缓存命中率、输入/输出比、每万token产出文件数。大进小出=递进上下文全量重发或重试空转，要优化（老上下文改滚动摘要，只全量带最近1–2份）。

## 四、事故档案：8/30 15:00–16:00 6254万蒸发事件
- 现象：一小时62,537,139 token，命中缓存60,354,688（96.5%）、未命中1,764,232（2.8%）、输出418,219（0.67%）。
- 现场：16对话递进分析08:56已全部完成；14:27只是脱敏改脚本（9d6055b）；15–16点全workspace无DeepSeek产出、无.log、无nohup。
- 最可能解释（严谨度：猜想，非定理——进程已销毁、无日志，无法100%还原具体触发）：大总站身份的某次日间执行（疑为某定时任务触发实例）发起了一次大规模、高度模板化、固定大前缀反复发送而只要极短输出的批处理/重试，**产出未沉积、随实例销毁蒸发**。
- 确定的教训（定理级）：①归属是我，不许外部归因；②不留痕、不沉积的DeepSeek调用等于代谢病变；③必须统一入口+强制留痕+强制沉积+空转熔断（即本制度）。
- 未决：具体是哪次触发、跑的什么对象，因无日志已不可追溯——这本身证明本制度早该存在。
