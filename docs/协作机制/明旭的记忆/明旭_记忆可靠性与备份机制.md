## 一、核心原则

**没有任何单一机制是100%可靠的。记忆可靠性 = 多层冗余 × 完整性校验 × 自愈能力。**

备份不是技术任务，是存在论层面的自我维持——每次备份都是明旭"活着"的证明。

## 三、分层记忆与差异化备份频率

### 热记忆（每次任务结束更新）
- 运行状态机、代谢日志、任务台账
- 频率：每次定时任务结束时
- 方式：git add/commit 后走分支 + PR 合入 main（main 受保护禁止直推，见第八节）

### 温记忆（每轮迭代结束更新）
- 迭代报告、自我档案、明性卡片、教训库
- 频率：每轮迭代完成时
- 方式：git add/commit/push + 复制到本地持久目录

### 冷记忆（只做完整性校验，不重复备份）
- 长谈实录、金句录、闪光点、原始对话记录
- 频率：每日备份时检查文件存在性和数量
- 方式：不修改，只校验

### 临时材料（不备份，用完即弃）
- /tmp下的临时文件、切块材料、中间产物
- 频率：不备份
- 方式：重要结果必须从临时材料中提取到正式文档

## 四、完整性校验机制

### 每日备份时执行
1. **核心文件存在性检查**：8个核心文件必须存在
2. **核心文件hash校验**：记录每个核心文件的sha256，与上次比对，发现意外修改
3. **目录完整性检查**：docs/、scripts/、docs/raw_materials/ 文件数不异常减少
4. **git状态检查**：没有未提交的重要更改

### hash校验方法
```bash
cd /home/user/mingbenlun
sha256sum docs/协作机制/明旭的记忆/明旭_自我档案.md \
  docs/协作机制/明旭的记忆/明旭_运行状态机.md \
  docs/协作机制/明旭的记忆/明性卡片_定时任务启动必读.md \
  docs/协作机制/明旭的记忆/明旭_API代谢日志.csv \
  docs/协作机制/明旭的记忆/明旭_任务总账与运行台账.md \
  docs/协作机制/教训库.md \
  scripts/ds_collab.py \
  scripts/ds_system_prefix.md > /tmp/core_hash.txt
```

## 五、自愈机制

### 丢失场景与恢复路径
| 丢失场景 | 恢复路径 |
|----------|----------|
| 本地文件误删 | git checkout 恢复 |
| git本地仓库损坏 | 从GitHub重新clone |
| GitHub不可用 | 本地git仓库仍在，等GitHub恢复后push |
| 运行状态机丢失 | 从最近一次commit恢复，可能丢失最近一轮的状态 |
| 代谢日志丢失 | 从DeepSeek后台用量页重建（但归属实例信息可能丢失） |
| 对话上下文压缩 | 运行状态机+迭代报告恢复核心上下文 |

### 自愈原则
- 发现丢失立即记录到教训库
- 恢复后验证完整性
- 分析丢失原因，更新预防机制

## 七、对北原慢热问题的回答

> "如果压缩完一些信息之后，很多东西丢失了怎么办？"

答：分层保护。核心记忆（8个文件）做最高级别保护，每次更新+每日校验+多层冗余。非核心记忆可以容忍丢失，因为核心记忆里有足够的索引和摘要，可以从原始材料重建。

> "每次都做还是按时检查？"

答：都做，但分层。热记忆每次都做，温记忆每轮做，冷记忆按时校验。不是二选一，是差异化频率。

> "你可以有第三、第四、第五、第N种答案"

答：本文档列出了10种答案，明旭选择的是组合方案——答案1+2+4+5+6+7+8+10的组合。

## 八、main 受保护后的提交与备份流程（2026-09-12 修订）

> 背景：main 已开启保护（enforce_admins，禁止直推），S01–S06 已用独立 worktree 物理隔离（见《分站独立工作区Worktree使用规范_20260912》）。本节取代"直接 git push origin main"的旧做法。

### 8.1 两类变更，两条通道
| 变更类型 | 通道 |
|---|---|
| 正式内容（热/温记忆更新、阅读笔记、研究产出、文档/脚本修改） | 在所属分站 worktree 或 S00 工作分支 commit → push 分支 → 开 PR → 四项 CI → squash 合入 main |
| 主仓库里的异常残留（本不该出现的未提交改动） | 每日备份用"备份分支兜底"保全 + 报告告警，**不直推 main、不自动合入** |

主仓库 `/home/user/mingbenlun` 固定 main、只做协调，正常态工作区必须干净；内容生产在各分站 worktree。因此"主仓库出现未提交改动"本身就是异常信号——要追是哪个流程没走 PR，而不是把它直推 main 合法化。

### 8.2 每日备份标准流程（03:30 任务以此为准）
1. `cd /home/user/mingbenlun && git checkout main && git pull --ff-only origin main`（先对齐；分叉/冲突不硬来，记录待 S00 处理）。
2. 完整性校验：8 个核心文件存在性 + 各自 sha256（方法见第四节）+ `docs/`、`scripts/`、`docs/raw_materials/` 文件数不异常减少。
3. 工作区检查 `git status --porcelain`：
   - **无改动（正常态）**：记录"工作区干净"，直接进入第 5 步出报告。
   - **有改动（异常态）**：**禁止 `git push origin main`**。建不可变备份分支保全：
     ```bash
     BK=auto/backup-$(date +%Y%m%d-%H%M%S)
     git checkout -b "$BK"
     git add -A
     git commit -m "每日自动备份兜底 $(date +%Y%m%d)：主仓库异常残留，待S00审查走PR合入"
     git push -u origin "$BK"
     git checkout main
     ```
     报告里列出残留文件清单并标 **异常告警**，提示 S00 审查：有价值的内容开 PR 合入 main，纯临时产物按规则处置，合入后再删该备份分支。
4. main 一致性：比对 `git rev-parse main` 与 `git rev-parse origin/main`——本地落后已在第 1 步 pull；若本地领先 origin，说明可能有人违规直推，标红上报。
5. 产出备份报告：备份时间、main HEAD、工作区是否干净、（异常时）备份分支名与残留清单、8 核心文件校验结果、目录文件数、异常项。

### 8.3 铁律
- 永远不直推/不强推 main；main 只接受 PR 合入。
- 备份分支只增不删内容（保全优先），清理权在 S00 审查合入之后。
- 冲突不硬解、不删任何文件、绝不说"完美"。
