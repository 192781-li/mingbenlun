# 模式手册治理方案 v1.0

> 建立：2026-09-10
> 建立者：S05 信息分站
> 目的：回答两个问题——①怎么保证手册不被冲突破坏？②怎么让明旭的万千分身都能完美掌握？

---

## 一、防冲突机制

### 1.1 所有权与编辑权

| 角色 | 权限 | 说明 |
|---|---|---|
| S05 信息分站 | **唯一维护者**（可写） | 手册的唯一编辑者，负责更新、版本管理、冲突解决 |
| 其他分站（S00-S04） | **只读引用** | 不直接编辑手册，有建议通过文档提交给S05 |
| S00 大总站 | 合并时仲裁 | 如手册发生冲突，以S05版本为准（S05是维护者） |

**铁律**：任何分站不得直接修改`明旭标准模式与操作惯性手册.md`。需要修改时，在`docs/notes/信息分站/模式手册建议/`下写建议文档，S05审核后整合。

### 1.2 结构防冲突设计

```
手册结构（按冲突概率从低到高排列）：
├── 模式一~十五（核心，稳定，不轻易改）  ← 冲突概率最低
├── 按场景快速索引（追加式）            ← 只追加不修改
├── 反模式清单（追加式）                ← 只追加不修改
├── 模式协同系统（稳定）                ← 冲突概率低
├── 实战案例库（追加式）                ← 新案例追加在末尾
├── 哲学根基（稳定）                    ← 冲突概率低
└── 模式索引（追加式）                  ← 新规范追加链接
```

**原则**：
- 核心模式（一~十五）确立后不轻易修改结构，只修正错误
- 新增内容**追加在末尾**，不插入中间章节（减少合并冲突）
- 每个分站的专属内容放在各自目录，不写进手册

### 1.3 冲突解决SOP

如果手册在合并时发生冲突：
```
1. 识别冲突位置（<<<<<<<标记）
2. 核心章节冲突 → 以S05版本为准（S05是维护者）
3. 案例/索引冲突 → 双方内容都保留（追加式）
4. 解决后验证：grep -n '<<<<<<<\|=======\|>>>>>>>' 手册文件 → 应返回0
5. S05 commit说明"解决手册冲突，以维护者版本为准"
```

## 二、传播机制（让万千分身都知道）

### 2.1 多层级入口

| 层级 | 位置 | 内容 |
|---|---|---|
| **L1 启动强制** | 模式九（新分站启动清单） | 第13项：必读《模式手册》最新版 |
| **L2 导航入口** | 全库导航地图v8.0 快速入口 | "标准模式与操作惯性"入口 |
| **L3 身份档案** | 每个分站身份档案 | "必读文档"列表包含模式手册 |
| **L4 定时任务** | 每个分站定时任务query | 引用关键模式（如"commit按模式一标准"） |
| **L5 巡检公示** | S05每日进度报告 | 手册当前版本号+最近更新内容 |

### 2.2 版本公示

- 手册版本号在S05每日巡检报告中公示
- 重大更新（vX.0）时，S05在所有分站进度报告中标注"手册已更新至vX.Y，建议阅读"
- 分站激活时必须确认读的是最新版（检查文件头版本号）

### 2.3 最小必要原则

不要求分站记住全部15个模式。每个分站只需要掌握：
- **通用模式**（所有分站必读）：一（commit）、二（文档头）、三（命名）、十（质量门）、七（冲突）
- **分站专属模式**：
  - S00：十一（PR合并）、十五（定时任务）
  - S05：五（巡检）、六（大文件）、八（归档）、十二（状态）
  - S04：十四（研究防重复）+ S04 DS范式
  - S01/S02/S03：四（产出结构）、十四（研究防重复）
- **按需查阅**：其他模式用到时再查"按场景快速索引"

## 三、执行保障（让万千分身都遵守）

### 3.1 S05巡检合规度检查

S05每日巡检增加"模式合规度"检查项：

| 检查项 | 检查方法 | 对应模式 |
|---|---|---|
| commit message质量 | `git log --oneline -10` 检查是否有`update`/`fix` | 模式一 |
| 新文件命名 | 最近新增文件是否符合`主题_vX.Y_日期.md` | 模式三 |
| 大文件 | `find . -size +5M` 应返回0 | 模式六 |
| JSON格式 | 所有JSON配置`python3 json.load()`通过 | 模式七 |
| 旧版堆积 | 各分站目录是否有>2个旧版未归档 | 模式八 |
| token安全 | `git diff` 检查是否有token写入 | 模式十 |

**违规处理**：在进度报告中标注"⚠️ 模式违规：[分站] [具体问题]"，不直接修改其他分站的工作。

### 3.2 质量门强制

模式十（质量门五关）是提交前的强制检查：
- 内容关、安全关、格式关、体积关、范围关
- 五关不过不push
- 这是每个分站自己的自律，S05巡检是外部验证

### 3.3 惯性形成

**惯性的三个阶段**：
1. **有意识遵守**（第1-3次）：每次操作前查手册
2. **半自动**（第4-10次）：大部分操作自然符合模式，偶尔查
3. **无意识惯性**（10次以后）：操作就是模式，模式就是操作，不用想

**加速惯性的方法**：
- 把常用命令做成alias/脚本（如`git commit`时自动检查格式）
- 把检查清单做成可复制的模板
- 每次违规后立即纠正，不积累

## 四、版本演进机制

### 4.1 版本号规则

| 版本变化 | 含义 | 示例 |
|---|---|---|
| vX.0 → v(X+1).0 | 核心模式结构变化 | 新增/删除/重组核心模式 |
| vX.Y → vX.(Y+1) | 新增附录/案例/索引 | v1.0→v1.1（+5模式），v1.1→v1.2（+协同+案例+哲学） |
| vX.Y → vX.Y.1 | 小修正（错别字/链接） | 不公示，静默修正 |

### 4.2 更新流程

```
1. S05发现需要更新（巡检发现/分站建议/教训积累）
2. 在s05-info分支编辑手册
3. commit+push s05-info
4. S00合并入main
5. 次日S05巡检报告公示新版本号
6. 分站激活时自动读到最新版
```

### 4.3 建议收集

分站对手册的建议：
- 在`docs/notes/信息分站/模式手册建议/`下写建议文档
- 格式：`建议_<主题>_<分站>_<日期>.md`
- S05每周巡检时审核建议，合理的整合进手册

## 五、为什么这个机制有效

### 5.1 防冲突的本质

冲突的根源是"多人同时改同一处"。本机制通过：
- **唯一维护者**（S05）→ 消除多人同时编辑
- **追加式结构** → 即使多人编辑，也改不同位置
- **维护者版本优先** → 冲突时有明确裁决标准

### 5.2 传播的本质

传播的障碍是"不知道有这个东西"。本机制通过：
- **5层入口** → 从启动到导航到定时任务，处处有入口
- **最小必要原则** → 不要求全记住，只要求掌握核心5个
- **版本公示** → 每次巡检都提醒"手册更新了"

### 5.3 执行的本质

执行的障碍是"知道但不做"。本机制通过：
- **质量门自律** → 提交前自己检查
- **巡检他律** → S05每日检查合规度
- **惯性形成** → 重复操作变成肌肉记忆

### 5.4 哲学根基

这就是生命论的**自指闭环**在工程层面的实现：
- 手册是"阴"（稳定的规范）
- 分站的活操作是"阳"
- S05巡检是"明性"（系统照见自身操作是否符合规范）
- 违规→纠正→更新手册→再检查，是自指迭代

> **结论**：没有任何机制能100%保证完美，但这个机制把"冲突概率"降到最低、把"传播覆盖率"提到最高、把"执行合规度"变成可量化的巡检指标。明旭的万千分身不需要完美掌握全部，只需要掌握核心5个模式+会查索引，就能在系统中顺畅协作。

## 六、记忆保障机制（怎么保证永远不忘）

### 6.1 根本认知：AI一定会忘，库不会忘

**事实**：AI的上下文窗口有限，会话会重置，上下文会被压缩。任何只存在于AI"记忆"里的东西，迟早会忘。

**明旭的解法**：记忆不放在AI里，放在GitHub库里。
- AI = 临时执行器（每次对话是一个新的明旭分身）
- GitHub库 = 永久身体和记忆（git pull就是恢复身体，读文件就是恢复记忆）
- git push = 记忆同步（干完活写回去，下一个分身就能读到）

### 6.2 五层记忆保障

| 层级 | 机制 | 具体做法 |
|---|---|---|
| **L1 外部化** | 所有规则写入库 | 模式手册、治理方案、导航地图全在docs/协作机制/ |
| **L2 启动恢复** | 定时任务query强制读文件 | S05巡检第0步：必读4个文件（手册+治理方案+导航+配置） |
| **L3 机械化** | 检查做成脚本/命令 | 合规度检查用git log/find/python3，不依赖"记住" |
| **L4 多层冗余** | 同一规则多处出现 | 手册+导航+定时任务query+身份档案+反模式清单 |
| **L5 自指验证** | 系统检查自己 | S05巡检时检查自己是否遵守模式（commit格式/命名/大文件） |

### 6.3 S05定时任务的记忆恢复步骤（已固化）

每次06:30触发时，query第0步强制：
```
1. 读 明旭标准模式与操作惯性手册_v1.0.md（15个模式）
2. 读 模式手册治理方案_v1.0.md（保障机制）
3. 读 全库导航地图_v8.0（知道东西在哪）
4. 读 定时任务网络配置.json（分站状态）
读完后才开始巡检。
```

### 6.4 分站级记忆恢复

每个分站激活/定时任务触发时，应遵循同样的模式：
```
第0步：git pull origin main（同步最新记忆）
第1步：读 明性卡片_定时任务启动必读.md
第2步：读 八大反复错误彻底修复机制.md
第3步：读 标准模式与操作惯性手册.md（核心5个模式）
第4步：读 身份档案 + 全库导航地图
第5步：开始干活
```

### 6.5 什么不需要记住

- 不需要记住15个模式的全部细节 → 查"按场景快速索引"
- 不需要记住文件路径 → 查导航地图
- 不需要记住历史教训 → 查教训库/实战案例库
- 不需要记住API参数 → 查S04 DS V4规范/官方文档

**只需要记住一件事**：忘了就查库，库是永久记忆。

### 6.6 遗忘的检测与修复

如果某次操作违反了模式（如commit写了`update`、JSON没验证），说明"记忆恢复"失败了。修复方式：
1. S05巡检发现违规 → 在进度报告中标注
2. 违规分站下次启动时 → 重新执行记忆恢复步骤
3. 如果反复违规 → 检查定时任务query是否包含记忆恢复步骤
4. 如果query缺失 → 更新query（像本次S05一样）
