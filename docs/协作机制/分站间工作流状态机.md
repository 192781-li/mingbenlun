# 分站间工作流状态机与文件归属权（唯一权威，两站共同遵守）

> **目的**：S01和S04在GitHub库上自动流转，不需要主人协调。杜绝互相覆盖、信息丢失、重复劳动。
> **最后更新**：2026-09-10

---

## 一、文件归属权（谁写谁读，越权=事故）

| 文件 | 写者 | 读者 | 写入方式 | 禁止 |
|---|---|---|---|---|
| `S01_运行指令.md` | **只S01** | S01、S04可读 | S01可改 | S04禁止修改 |
| `S04_运行指令.md` | **只S04** | S04、S01可读 | S04可改 | S01禁止修改（S01要给S04指令→写S01_to_S04.md） |
| `S01_to_S04.md` | **只S01追加** | S04每轮读末尾 | append-only | S04禁止改/删/重排；S01不修改已有条目 |
| `S04_to_S01.md` | **只S04追加** | S01每轮读末尾 | append-only | S01禁止改/删/重排；S04不修改已有条目 |
| `智慧结晶库.md` | 双方都可追加 | 双方 | append-only，编号递增 | 禁止修改对方写的结晶 |
| `河流主干.md` | 双方都可追加 | 双方 | append-only | 禁止删除已有记录 |
| `河流状态.md` | 双方都可更新 | 双方 | 可改（当前状态） | 改前先pull |
| `定时任务网络配置.json` | 双方 | 双方 | S01只改assigned_to=S01的任务；S04只改assigned_to=S04的任务 | 禁止改对方任务 |
| `S01_signal.json` | 只S01 | S04可读 | S01可改 | S04禁止写 |
| `S04_signal.json` | 只S04 | S01可读 | S04可改 | S01禁止写 |
| `coq/theories/ALL/Layer*.v` | S04主写，S01紧急时可直接写证明 | 双方 | S01写后必须在S01_to_S04.md登记 | S04不许删S01的证明（只能tactic级小修） |
| `docs/notes/Coq形式化/` | 双方 | 双方 | 各自建文件，不覆盖对方文件 | — |

**核心原则**：要给对方东西，写进自己的通信通道文件，不写进对方的运行指令。对方的运行指令只有对方能改。

## 二、状态机（S01↔S04协作的完整状态转换）

```
状态A：S04正常推进（看板驱动，DS主谋）
  │
  ├─ DS≤2轮收敛 → 看板done → 继续下一个J（回到状态A）
  │
  ├─ DS>2轮无进展 / 哲学判断点 / 根本性卡点
  │   ↓
  │   S04动作：
  │   ① 写卡点到 S04_to_S01.md（append）
  │   ② task_queue注入assigned_to=S01 urgent任务（双保险）
  │   ③ S04_signal.json: needs_s01=true
  │   ④ S04切去做不依赖该卡点的其他J（不等S01）
  │   ↓
状态B：等待S01（S04不阻塞，做别的）
  │
  │   S01下次触发检测到：
  │   ① S04_to_S01.md末尾有新条目
  │   ② task_queue有S01 urgent pending
  │   ↓
状态C：S01直接介入（隐藏启动，跳过常规哲学写作）
  │   S01动作：
  │   ① 切s04-coq，pull最新
  │   ② 读卡点+coqc错误+Layer定义
  │   ③ 定义语义审计→操作权流动分析
  │   ④ 直接写证明/给精确策略/做方向裁定
  │   ⑤ commit push
  │   ⑥ 写 S01_to_S04.md（append，登记产出）
  │   ⑦ task_queue标记completed
  │   ⑧ S01_signal.json更新
  │   ↓
状态D：S04验证（S04下次触发检测到S01_to_S04.md新条目）
  │   S04动作：
  │   ① 读S01_to_S04.md末尾条目
  │   ② git pull拿S01证明
  │   ③ coqc编译验证（不调DS）
  │   ├─ 通过 → 看板done → S04_to_S01.md写验证结果 → 继续推进（回到状态A）
  │   ├─ tactic级小错 → S04自己修（不调DS）→ coqc通过 → 回到状态A
  │   └─ 根本性错误 → S04_to_S01.md写错误详情 → 回到状态B
  │
  └─ S04全部J做完 → L层清零 → 读S01_to_S04.md的L3-L8预判 → 进入下一层（回到状态A）
```

## 三、每轮开工检查顺序（硬编码到各自运行指令）

### S04每轮开工
1. git sync + river_sync pull
2. **读S01_to_S04.md末尾**（有没有S01新条目→有则进入状态D验证，优先于看板取活）
3. 读S04_运行指令.md
4. 看板取活
5. DS主谋闭环
6. 回写（signal/河流主干/结晶库追加）
7. 有卡点→写S04_to_S01.md+注入task_queue

### S01每轮开工
1. git sync + river_sync pull
2. **读S04_to_S01.md末尾**（有没有S04新条目→有则进入状态C直接介入，优先于常规哲学研究）
3. **检查task_queue**（assigned_to=S01 urgent pending→进入状态C）
4. 无紧急→常规哲学研究
5. 回写（signal/河流主干/结晶库追加）
6. 给S04的东西→写S01_to_S04.md

## 四、冲突预防

1. **不同分支工作**：S01在s01-philosophy，S04在s04-coq。river_sync.sh负责同步docs/下的协作文件。
2. **append-only文件用时间戳+编号**：不修改已有条目，只追加新条目，从根上杜绝冲突。
3. **Layer*.v代码冲突**：S01紧急直接写证明前先pull最新；S04拿到S01证明后只做tactic级小修，不重写整个证明。
4. **如果rebase冲突**：append-only文件的冲突=双方都追加了内容，解决方案=两边都保留，按编号排序。运行指令文件冲突=各自保留自己的部分，对方的部分从通信通道读。
5. **commit message标注来源**：S01的commit以"S01:"开头，S04的以"S04:"开头，一眼可辨。
