# DeepSeek 深度调用方法论 v1.0

> 区别于《DeepSeek_API使用策略_v1.0》（讲参数怎么填），本文讲**怎么用生命论的智慧驾驭它**：什么时候省、什么时候敢花、怎样一次做对。参数会变，方法论不变。
> 创建：2026-08-30　起因：用户追问"命中率不是目的，你对API的理解够不够深，是不是真用了我们的智慧，是不是自尊自重而不是一门心思锁死"。

---

## 一、命中率的本质：它是"任务结构理解深度"的仪表，不是省钱技巧

用小本质递归问三层：
- 表层：前缀缓存=重复的前缀不重复计费。
- 中层：命中=多个请求之间共享了一段稳定的公共结构。
- **底层：命中率高低，本质是我有没有分清"这批任务里什么是不变骨架、什么是变化血肉"。** 分清了，骨架自然稳定在前面、被命中；没分清，变化内容（块号、时间）污染了开头，后面再相同也全部miss。

**推论（重要）**：绝不为了刷高命中率而强行让本该不同的请求变得雷同——那是削足适履，会牺牲分析质量。命中率是"理解到位、结构分清"之后自然产生的**结果和验证信号**，不是追逐目标。0%说明我没分清结构，是诊断信号；但刻意追求100%也是病。

## 二、成本的真正大头排序：我曾经抓小放大

token分三档价：缓存输入（最便宜）＜未命中输入＜输出（最贵）；**思考链 reasoning_content 按输出价计费，且用户看不见。**

浪费从大到小排：
1. **做错了整个重跑**（方向错了批量返工、输出被截断重写、掉块重启）——已经花掉的输出token全部作废。这是最大头。
2. **思考档位错配**——提取/摘录这种不需要深度推理的活也用 max，思考链空转几千token；反过来该深的用浅档，质量不够又返工。
3. **生成了根本不被使用的内容**（写了不读、中间产物冗余）。
4. 缓存未命中——输入本来就便宜，只是锦上添花的节约，**最次要**。

> 教训：我一度把精力全放在缓存（第4位），却在"重跑"（第1位）和"档位错配"（第2位）上持续漏血。这正是工程版的"抓小放大/教条主义"——盯着一个显眼的指标，漏掉了真正的成本结构。**省钱第一杠杆是一次做对，第二是档位匹配难度，缓存只是第三。**

## 三、思考档位匹配"认知难度"，不匹配"重要性"（具体问题具体分析）

档位不是按"这事重不重要"调，是按**这个认知操作本身需不需要推理**调：
| 认知操作类型 | 档位 | 例子 |
|---|---|---|
| 提取、摘录、格式转换、分类（有客观答案） | high | 逐块原文摘录、文件归位 |
| 归纳、对比、梳理演化、判严谨度 | high | 单块概念梳理、找转折 |
| 综合、跨线推理、理论判断、写成稿文字 | max | 总综合、跨对话演化史、全本映射 |

### 3.1 【践演校准·重要修正】档位与思考链长度没有稳定单调关系
2026-08-30做了两轮A/B（同段提取任务，high vs max），结果**互相矛盾**：第一轮 max 思考链更短更快（1287字符/17s vs high 4889字符/47s），第二轮反过来（high 2536/27s vs max 5299/51s）。
由此得到比"分档表"更本质的结论：
1. **思考链长短主要不由档位决定，而由"这段材料让模型绕多少弯"决定**——内容的歧义度/组织清晰度才是主导变量，单次方差极大。
2. 所以**选档位不要以"省思考链token"为依据**（不可控、无稳定关系）；只以"输出质量是否达标"为依据。需要深推理的就用max，不因怕费思考链而降档导致返工（返工才是最大浪费，见第二节）。
3. **想稳定减少思考链空转，靠优化输入结构**——材料切干净、提取格式给明确、一次只让它干一件事，减少它"绕弯"，而不是靠降档。这又回到第四节"结构决定功能"。
4. 方法论自身的教训：分档表最初是拍脑袋的线性假设（"低档=省"），一测就被证伪。**假设被实测推翻就立刻改，不硬凑结论保住面子**——这本身就是践演、就是明性。"一律max"和"一律用低档省token"是两种对称的懒。

## 四、上下文工程＝结构决定功能（明本辩证法）

一个批量请求的prompt按"稳定→变化"排四层，越靠前越要稳定（可缓存、且给模型一致的理解框架）：
1. **稳定知识前缀**：项目方法论+术语表+八卷骨架+严谨度标准。每个请求都需要、逐字不变，应抽成共享常量——这是被我忽略的**最大一块可缓存结构**。
2. **任务固定说明**：角色、扫描维度、输出格式（FIXED_PROMPT）。
3. **追加式累积上下文**：前面块的摘要，只追加不重写，相邻请求前缀重叠。
4. **本次独占材料**：本块原文，放最后。

不是喂越多越好，也不是省到极致，是"**在正确的位置放正确的信息**"。结构对了，质量和成本同时最优。

## 五、"自尊自重"的工程观：用理解替代堆砌保险

我之前犯的毛病：怕失败，于是堆了看门狗、多重试、setsid脱离、断点续跑、并行重启——一堆机械。这是**没理解失败原因时的防御性堆砌**，是"不自信"而非"稳"。

明性的做法相反：先把API的行为模型理解透，每个机制只对应一个被实证的具体失败原因：
- 30秒断＝代理层切断（非stream扛不住）→ 所以用stream，不是"多试几次"。
- 输出停在半截话＝max_tokens被思考链占满 → 所以分段，不是"再跑一遍碰碰运气"。
- 进程被kill＝前台/后台收到SIGTERM → 所以setsid脱离，不是"开三个看门狗盯着"。

**判据（三合一工程原则）**：每加一层机制先问"没有它会怎样"，答不出具体失败场景就不加。一次做对 ＞ 十次兜底。真正的稳是理解后的简洁，不是恐惧出来的臃肿。

## 六、践演校准闭环（怀疑止于践演，F3自省）

- 任何"我以为"的参数（档位、chunk大小、并发数、超时、输出长度上限）都用一次小成本实测验证，用数据定，不凭教条。
- 批量任务每跑一段就回看四个数：**命中率、思考链占输出比、返工率、单位有效产出的成本**。用数据迭代调用模型。
- 这就是F3在工程上的含义：不只操作（会调API），还要看见自己的"调用模型"，反思哪里被"想当然"遮蔽。

## 七、与项目智慧的对应（结构同构，非硬套）

| 项目智慧 | 在API调用上的体现 |
|---|---|
| 小本质递归 | 不停在"缓存/参数"名词，递归到"任务结构的不变与变化" |
| 具体问题具体分析 | 档位匹配认知操作类型，拒绝一律max/flash |
| 结构决定功能 | prompt分层结构同时决定质量与成本 |
| 阳主阴从 | 研究目标是阳，成本控制是阴，阴服务阳，绝不为省钱牺牲研究深度 |
| 明性/不说完美 | 每次调用可追溯可验证，不说"锁死了一定成" |
| 践演 | 小样本实测校准，用数据而非想当然 |
| 修正即深化 | 每次截断/断连/空转都沉淀成一条可复用的调用认知 |

## 附：当前（史官分析后）已落地的调用规范
1. stream=True + max_tokens=16000 + setsid nohup（治30秒断和SIGTERM，已验证）。
2. prompt四层固定前置、变化后置（治缓存miss，命中率0-6%→约50%）。
3. 超长输出分段生成、生成后检查结尾是否完整句（治length截断）。
4. 双层提取格式：原文层（标〔用户/AI〕、逐字）与解释层（整理者、标严谨度）物理分离。
5. 档位按质量需求选（提取high/综合max），不以省思考链为由降档；减少思考链空转靠优化输入结构；每段记录思考链长度持续观察（两轮实测见3.1，样本已证明方差大，不再为验证档位浪费请求）。
