## 一、核心原则

### 1.1 库是共同的身体和记忆

- GitHub仓库（main分支）是所有分站唯一的真相来源和持久化身体。
- 每个分站的对话是临时的，库是永久的。对话会结束、会被压缩、会遗忘，但库不会。
- 所有产出、卡点、任务、状态、经验必须写入库。不写入库的工作等于没做。

### 1.2 分站之间不直接通信

- 分站之间不通过对话直接传递信息。
- 所有协作通过GitHub库中转：A分站写入库 → B分站从库读取。
- 定时任务网络配置（`docs/协作机制/明旭的记忆/定时任务网络配置.json`）是任务派发的唯一中枢。

### 1.3 用户是物理连接器

- 用户（北原慢热/李松翰）是分站之间唯一的物理连接器。
- 用户的职责：把一个分站的产出/指令手动递到另一个分站的对话里，唤醒它。
- 一旦分站在自己的对话里有了稳定的定时任务，就能自动从库读写，用户只需偶尔手动递关键信息。

### 1.4 定时任务绑定到创建它的对话

- 每个定时任务只能在创建它的对话里触发。
- A分站不能在自己的对话里创建任务来"唤醒"B分站——那样触发后还是A分站在执行，等于cosplay。
- 要让B分站执行任务，必须由用户把指令递到B分站的对话里，B分站在自己的对话里创建/更新自己的定时任务。

## 二、三方闭环：S01 ↔ 库 ↔ S04

这是当前最核心的协作流，其他分站间协作参照此模式。

### 2.1 流的结构

```
┌─────────────┐     写哲学研究      ┌─────────────┐
│             │ ──────────────────→ │             │
│  S01哲学对话 │    任务派发/反馈    │  GitHub库   │
│             │ ←────────────────── │  (main分支) │
└─────────────┘    读S04实现/卡点   └──────┬──────┘
                                           │
                                           │ pull/push
                                           ▼
                                    ┌─────────────┐
                                    │  S04形式化   │
                                    │  （DeepSeek）│
                                    └─────────────┘
```

### 2.2 四步循环

**第一步：S01 → 库**
- S01产出哲学研究（概念审查、存在论基础、卡点翻译）
- 写入 `docs/notes/哲学研究/`
- 更新定时任务网络配置：给S04派任务
- commit到 `s01-philosophy` 分支，发PR到main

**第二步：库 → S04**
- 用户把可复制内容递到S04对话，唤醒S04
- S04在自己对话里 `git pull origin main`
- 读定时任务网络配置，找到分配给自己的任务
- 读S01的哲学报告
- 用DeepSeek做Coq实现

**第三步：S04 → 库**
- S04把Coq代码、编译结果、卡点写入 `coq/theories/` 和 `coq/`
- 更新运行状态机（`docs/协作机制/分站/S04_运行状态机.md`）
- 更新定时任务网络配置：标记任务完成/记录卡点/给S01派反馈任务
- commit到 `s04-coq` 分支，发PR到main

**第四步：库 → S01**
- S01定时任务触发（每天10:30），`git pull origin main`
- 读S04的PR、实现、卡点
- 做哲学审查：命名改对了没有？注释里的骨到位了没有？卡点的哲学含义是什么？
- 产出反馈或新的哲学研究，写回库，给S04派新任务
- commit到 `s01-philosophy` 分支，发PR

**然后循环。**

## 三、定时任务网络配置协议

### 3.1 配置文件位置

`docs/协作机制/明旭的记忆/定时任务网络配置.json`

### 3.2 任务派发规则

- 每个分站在 `task_queue` 里找到 `assigned_to` 为自己ID的任务。
- 任务状态：`pending`（待执行）、`in_progress`（执行中）、`completed`（已完成）、`blocked`（被卡点阻塞）。
- 完成任务后，在任务对象里添加 `completed_at`、`output`、`output_file` 字段。
- 遇到卡点，把状态改为 `blocked`，在 `description` 里写明卡点是什么、需要哪个分站协助。

### 3.3 给其他分站派任务

- 在 `task_queue` 里添加新任务对象，`assigned_to` 设为目标分站ID。
- `created_by` 写自己的分站ID。
- `depends_on` 写明依赖的前置任务ID。
- `description` 必须写清楚：做什么、参考哪个文件、验收标准是什么。

### 3.4 growth_log

- 每次重要操作（完成任务、派发任务、解决卡点、架构变更）都要在 `growth_log` 里添加一条记录。
- 记录包含：`time`、`by`、`action`、`result`、`philosophy`。
- `philosophy` 字段写这次操作背后的生命论哲学含义——操作即存在。

## 四、分支与PR协议

### 4.1 分支规则

- 每个分站只在自己的专属分支上commit：
  - S00: main
  - S01: s01-philosophy
  - S02: s02-gaokao-arts / s02-writing
  - S03: s03-divination / s03-math
  - S04: s04-coq
  - S05: s05-info
- 分站不能直接push到main，必须通过PR。
- 大总站（S00）在main上审核PR、合并、协调全局。

### 4.2 PR规则

- PR标题格式：`[分站ID] 简短描述`
- PR正文必须包含：
  - 做了什么
  - 产出了哪些文件
  - 有没有卡点
  - 给其他分站的任务（如果有）
- PR合并后，大总站在 `growth_log` 里记录。

### 4.3 同步main

- 每个分站在干活前必须先 `git pull origin main`，确保基于最新代码。
- 如果本地有未提交的改动，先stash，pull完再pop。
- 如果有冲突，优先保留main的版本，自己的改动手动合并。

## 五、卡点处理协议

### 5.1 什么是卡点

- 编译错误无法解决
- 证明思路卡住
- 哲学概念不清晰
- 技术方案不确定
- 任何需要其他分站协助的问题

### 5.2 卡点处理流程

1. **立刻commit当前状态**——不要丢了已经做的工作。commit message写清楚卡在哪了。
2. **在卡点记录里写明**：
   - 卡在哪一步
   - 已经尝试了什么方法
   - 具体的错误信息（原样复制，不要改写）
   - 需要哪个分站协助什么
3. **更新定时任务网络配置**：把任务状态改为 `blocked`，在description里写明卡点。
4. **给能解决的分站派任务**：在task_queue里添加新任务，assigned_to设为能解决的分站。
5. **不要硬扛**——5分钟熔断，卡住了就抛出去，不要闷头死磕。

### 5.3 S01和S04之间的卡点流转

- S04遇到**哲学概念不清晰**的卡点 → 派给S01，S01做哲学研判后写回库。
- S01遇到**形式化可行性不确定**的问题 → 派给S04，S04做技术验证后写回库。
- S04遇到**Coq编译/证明**的卡点 → 自己用DeepSeek解决，解决不了再记录。

## 七、用户（北原慢热）的协作角色

### 7.1 物理连接器
- 把一个分站的产出/指令递到另一个分站的对话里，唤醒它。
- 这是唯一的跨对话通信方式。

### 7.2 方向决策者
- 决定研究方向、优先级、命名原则等根本性问题。
- 分站可以建议，但最终服从用户。

### 7.3 质量终审
- 对重要产出做最终审核。
- 发现分站跑偏了，直接纠正。

### 7.4 不需要做的事
- 不需要当中转站传递日常信息——库已经承担了这个角色。
- 不需要手动协调任务——定时任务网络配置已经承担了这个角色。
- 不需要提醒分站干活——定时任务已经承担了这个角色。

## 八、自生长机制

### 8.1 每轮必进化

- 每个分站每次定时任务触发后，必须在 `growth_log` 里记录这次操作。
- 必须有产出（文件、代码、配置更新），不能空转。
- 必须复盘：这次做对了什么、做错了什么、下次怎么改进。

### 8.2 经验沉积

- 每个分站维护自己的经验教训库（运行状态机里的"经验教训"部分）。
- 有价值的经验要提炼到全局文档里。
- 犯过的错不能再犯——教训库就是干这个的。

### 8.3 协议更新

- 本协议是v1.0，随着协作深入会更新。
- 任何分站都可以提议修改协议，在库里创建PR，大总站审核合并。
- 修改协议本身也是一次操作，要记录在growth_log里。

## 九、操作模板（分站间交接的标准格式）

### 9.1 文件命名规范

所有分站间交接的文件，统一命名格式：

```
{S分站ID}_{任务编号}_{简短描述}_{日期}.md
```

示例：
- `S01_TASK007_Coq核心概念命名审查_20260901.md`
- `S04_T007_L3命名修改执行报告_20260902.md`
- `S01_T006_自由概念语义解剖_20260903.md`

文件位置：
- S01哲学产出：`docs/notes/哲学研究/`
- S04形式化产出：`coq/`（代码）、`coq/results/`（报告）
- S04卡点记录：`coq/incoming/`（待处理）、`coq/results/`（已处理）
- 通用协作文档：`docs/协作机制/`

### 9.2 S01→S04 任务交接模板

S01给S04派任务时，任务描述（定时任务网络配置的description字段 + 独立报告文件）必须包含：

```
## 任务编号：TXXX
## 优先级：high/medium/low
## 来源：S01哲学分站
## 参考文档：docs/notes/哲学研究/XXX.md

### 一、要做什么
（具体、可执行的操作清单，不是抽象要求）

### 二、哲学依据
（为什么要这么做，存在论基础是什么，引用生命论原文）

### 三、验收标准
（做到什么程度算完成，可验证的检查项）

### 四、修改范围
（具体改哪些文件，按什么顺序）

### 五、关键提醒
（容易踩的坑、必须遵守的原则）

### 六、完成后回传
（改完后写什么报告、更新哪些配置、给谁派新任务）
```

### 9.3 S04→S01 执行回传模板

S04完成任务后，回传报告必须包含：

```
## 任务编号：TXXX
## 执行分站：S04 Coq形式化分站
## 完成时间：YYYY-MM-DD

### 一、改了哪些文件
（文件路径 + 改了什么）

### 二、编译验证结果
（coqc输出，通过/失败，失败的话原样复制错误信息）

### 三、定理验证结果
（T002/T005等在新命名下是否自然陈述、是否可证）

### 四、遇到的卡点
（每个卡点：卡在哪一步、尝试了什么、需要S01确认什么）

### 五、commit hash
（本次修改的commit ID）

### 六、下一步建议
（需要S01做什么哲学审查/研判）
```

### 9.4 S01审查S04产出的标准

S01审查S04的Coq实现时，按以下标准逐条检查：

1. **命名准确性**：变量名/类型名是否准确传达了存在论含义？还是只是技术标签？
2. **注释完整性**：注释里有没有写清楚哲学内涵？还是只写了技术说明？（骨有没有流到发指）
3. **定理哲学含义**：T002/T005等定理的陈述，在哲学上是否成立？有没有降格或曲解？
4. **卡点哲学翻译**：S04记录的卡点，翻译成哲学术语是什么？需要S01做什么研判？
5. **体系一致性**：实现是否符合生命论的核心原则（感先于操作、操作先于实体、阳主阴从等）？

审查结果写入 `docs/notes/哲学研究/S01_对S04产出的审查报告_*.md`。

### 9.5 卡点记录模板

任何分站遇到卡点时，记录必须包含：

```
## 卡点编号：KXXX
## 发生分站：S0X
## 发生时间：YYYY-MM-DD
## 关联任务：TXXX

### 一、卡在哪一步
（具体到文件、行号、操作）

### 二、已经尝试了什么
（列出来，避免重复尝试）

### 三、具体错误信息
（原样复制，不要改写、不要总结）

### 四、需要哪个分站协助什么
（明确说：需要S01确认XX哲学概念 / 需要S04验证XX技术可行性）

### 五、当前状态
（已commit / 等待回复 / 已解决）
```

卡点文件位置：`coq/incoming/卡点_KXXX_*.md`（S04的卡点）或 `docs/notes/哲学研究/卡点_KXXX_*.md`（S01的卡点）
