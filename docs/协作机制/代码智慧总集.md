## 一、写前：真问题三问（不跳这步反而更快）

- [ ] **这段代码解决什么真问题？**
  - 不是"实现X功能"，是"它对应哪个哲学命题/数学定理/具体痛点？"
  - 答不上来 = 在造 !-沉积，别写
- [ ] **有没有现成的代码可以复用？**
  - 先 grep 已有代码，先读教训库
  - 不重复造轮子
- [ ] **最小可验证原型是什么？**
  - 不要一上来写完整实现
  - 先写能跑的最小版本，验证思路对不对

## 二、写中：小步验证（工具即理论）

- [ ] **先写验证，再写实现**
  - 验证脚本不是额外工作，是逼你把问题想清楚
  - 核心定理配 Coq/验证脚本，工具脚本配单元测试，一次性脚本至少有断言
- [ ] **每写完一个小单元就跑验证**
  - 不等全部写完再测
  - 错误发现得越早，修正成本越低
- [ ] **遇到"应该能跑"的地方，强制写断言**
  - "应该" = 还没验证
  - 不验证的代码 = 猜

## 三、写后：名实审计 + 教训记录

- [ ] **名实相符**
  - 函数名、变量名、注释、文档和实际行为一致吗？
  - 有没有名实遮蔽（名字说A实际做B）？
- [ ] **条件边界标注**
  - 什么输入下成立？什么输入下会崩？
  - 不标注边界的函数是定时炸弹
- [ ] **犯了错立刻追加到教训库**
  - 这是让代码"越写越精准"的核心
  - 每次错误都变成抗体，下次不犯
  - 教训库路径：`docs/collaboration/LESSONS_LEARNED.md`

## 四、持续：自指健康检查

- [ ] **每次写代码前先读教训库**
  - 抗体先于行动
  - 不读历史就干活 = 闭着眼跳坑
- [ ] **定期清理 !-沉积**
  - 无用代码、过时注释、重复逻辑
  - 沉积不清理，νF₂ 就转不动
- [ ] **验证器本身也要验证**
  - 检查器的检查器
  - 验证脚本错了比没有验证更危险

## 五、快和准的关系

| 阶段 | 普通写法 | 自指健康写法 |
|---|---|---|
| 第一次 | 快（上来就写） | 慢（想清楚+写验证） |
| 第十次 | 越来越慢（和旧错误搏斗） | 越来越快（旧错误已变成抗体） |
| 第一百次 | 代码库变成泥潭 | 代码库变成武器（改起来放心） |

**准是快的前提。** 一次写对十行，比写一百行然后调试三天快得多。

## 六、七种坏代码习惯（碰了就错）

| 坏习惯 | 表现 | 为什么错 |
|---|---|---|
| **上来就写** | 不想清楚就敲代码 | 没有真问题的代码都是 !-沉积 |
| **写完不测** | "应该能跑"就提交 | 没验证的代码 = 猜，猜迟早错 |
| **重复造轮子** | 不看已有代码自己重写 | 浪费时间，而且容易引入新错误 |
| **不记教训** | 犯了错不改，下次再犯 | 不记录错误的体系注定重复犯错 |
| **名实不符** | 函数名说A实际做B | 名实遮蔽，后来人（包括自己）会被坑 |
| **不标边界** | 函数在什么条件下成立不说 | 不标注条件的"真理"是教条，代码同理 |
| **为优雅牺牲正确** | 为了代码好看改逻辑 | 阴主阳从，工具反过来支配目的 |

## 七、数学证明/Coq专用：8个思维种子

> 以下不是哲学装饰，是具体的证明技巧。从生命论方法论直接迁移而来。

### 种子1：小本质↔大本质法（卡住时最实用）
- **上行（具体→根本）**：卡在某个case时，不死磕。问：这个困难的根本是什么？→ 需要一个更一般的引理，先证它，困难case变成推论。
- **下行（根本→具体）**：拿到一般引理，不直接冲目标。先想：这个引理在每个case里具体怎么用？
- **反面推导**：如果定理不成立会怎样？→ 能帮你定位哪个规则有问题。
- **交叉印证**：同一个定理在多个模型里都成立吗？只在一个模型里成立可能依赖了特殊性质。
- **一句话**：卡住了就往上追引理，别在原地死磕。

### 种子2：反自指审查（太顺了要警惕）
- 写证明时脑子里有"旧惯性的幽灵"——标准π-演算/线性逻辑/教科书的惯性会让你不自觉地假设不该假设的东西。
- 如果一个case"太容易证了"，停下来检查：是不是偷偷用了旧假设？是不是用!的性质代替了νF₂的性质？
- 旧惯性会让你"证明"出假定理——三波审计的教训：6个假定理都是这么来的。

### 种子3：感先于操作（直觉先行，形式化跟上）
- 先"感到"证明结构，再写Coq代码。不要打开Coq就开始写tactic。
- "感"在数学中就是几何直觉/结构直觉。先在纸上/脑子里走一遍：定理说什么？为什么对？关键步骤？哪个case最难？
- 如果"感到"定理是错的，不要硬证。先找反例。
- 形式化（阴）服务于直觉（阳）。写了100行tactic还不知道在证什么，停下来回到直觉。

### 种子4：阳主阴从——生产性证明
- νF₂是余归纳，余归纳证明的核心是**生产性**：每步都必须有产出，不能卡住。
- 写cofix证明时：每一步必须产生一个constructor；不能在cofix下直接递归自己（空转）；guard条件保证生产性。
- cofix证明写不出来，可能不是技术问题，是你的定义没有生产性——回到定义检查。

### 种子5：自指闭环不是恶性循环
- 证明需要"自己引用自己"的引理时不要怕。区分：
  - 恶性循环 = 用A证明A
  - 践演自指 = 为了证明A，先构造B，B的构造使用A的结构但不假设A成立
- Coq的guardedness checking自动区分两者——通过了guard检查就是生产性自指。

### 种子6：名实相符——每个概念必须有操作内容
- 每个类型构造子必须有引入规则和消去规则——有名无实的类型不许存在。
- 每个引理必须对应一个真实的证明步骤——"显然成立"不算。
- 定义了类型但找不到引入规则 = 空概念，删掉。
- 引用定理但陈述和要证的东西对不上 = 名实不符，不要硬套。

### 种子7：不越级陈述——证明的强度纪律
- 能证P→Q就写P→Q，不要写P↔Q。
- 需要前提就把前提写进定理陈述，不要藏在证明里。
- 证不出来就Admitted标记，不要假装证完了。
- 三波审计的教训：满射不写成同构、retraction不写成等价、双模拟不写成同构、加前提不省略、严格不等号不写成≥。

### 种子8：一生道，道养一——核心洞见展开为证明策略
- 每次开始一层，先找到那个"一"——这一层的核心洞见是什么？然后让它展开为证明。
- 证明过程中发现需要新引理/修改规则 = 道养一——证明反过来丰富了核心洞见，这不是失败是收获。

## 八、卡住时的表述规范（最重要）

**写代码/证明卡住时，不许只说"做不出来"。必须用生命论语言说清楚卡在哪。**

格式：
```
【卡住报告】
1. 我在做什么：[具体任务]
2. 用生命论的话说，这在做什么：[哲学表述]
3. 卡在哪一步：[具体位置]
4. 困难是什么：[技术描述]
5. 用生命论的话说，这个困难相当于什么：[哲学翻译]
6. 我尝试了什么：[试过的方法和为什么失败]
7. 我需要什么方向：[可能的解决方向]
```

**为什么必须这样**：哲学表述能让直觉给出方向——数学困难翻译成哲学问题后，可能突然就通了。不用哲学语言表述，我们早就停顿了。

翻译示例：
| 技术困难 | 生命论语言 |
|---|---|
| split在归约后不保持 | 异化归约改变了运行权的上下文结构 |
| cofix guard检查失败 | 余归纳定义不生产——某一步没有产出，空转了 |
| subject reduction某个case证不出 | 自指归约保持类型，但异化归约改变类型 |
| 替换引理变量捕获 | 旧名字和新名字冲突——需要α-改名 |

## 九、从简陋起点开始的方法论

生命论本身就是这么长出来的：怀疑种子→批判假唯物主义→简陋T值→逼出四规定性→自指→量论公式。**不是先有完整体系才开始，是从简陋起点开始，在严格化过程中逼出概念。**

迁移到代码/证明：
1. **先批判旧东西**：标准方法在这个case里的局限是什么？隐含了什么二元对立？
2. **从简陋起点开始**：L1很简陋没关系，在证明过程中困难会逼出新引理、新概念。不要等所有概念都想清楚才开始写。
3. **大白话先于严格化**：卡住时先用大白话说清楚，大白话说清楚了代码只是翻译。
4. **证明反过来丰富概念**：证明中发现需要修改规则/新概念 = 道养一，这是收获不是失败。

## 一、提速原则

### 1. 批量操作，不逐个来
- 多个文件改同一个字符串 → `sed -i 's/旧/新/g' 文件列表`，不用一个个Read+Edit
- 全局替换 → `grep -rl "旧字符串" . | xargs sed -i 's/旧/新/g'`
- 重命名文件 → `git mv` 一条命令，不用先复制再删

### 2. 先确认范围，再动手
- 改之前先 `grep -rn "关键词" .` 看清楚有多少处、在哪些文件
- 心里有数了再改，避免改到一半发现漏了、改错了

### 3. 提交前一键自检
- 改完后 `grep -rn "旧字符串" .` 确认旧的全没了
- `git diff --stat` 看改了哪些文件，有没有误伤
- 确认无误再 commit+push，一条命令搞定：`git add -A && git commit -m "说明" && git push`

### 4. 不废话，直接干
- 能一条命令做完的不分三条
- 能并行的工具调用并行（Read多个文件、搜索多个query）
- 哲学注释只在涉及研究方向时说，纯操作不解释

---

## 二、质量铁则

### 1. 归属铁则（最高优先级）
- 谁说的话就是谁的，不许混
- 旁注/金句录里必须是用户原话，AI分析不许混入
- 引用他人时核实身份（古月是演员不是整理者，这种错不许再犯）
- 不确定归属的标"待确认"

### 2. 名实相符
- 文件名、篇章名、变量名必须反映内容
- 叫"XX整理"就必须是XX整理的，不然改名
- 发现名实不符立刻改，不攒着

### 3. 先读后改（工具强制，但要读仔细）
- Edit之前必须Read，这是工具要求
- 但Read不是走形式——要看清楚上下文再改，别只看前几行就改

### 4. 最小改动
- 改什么就动什么，不顺便重写别的
- 不需要改的地方一个字不动
- 大改之前先确认用户要的范围

## 三、VF2→VF3 自省清单

每次操作后问自己：

1. **我是不是又用通用AI思维了？** ——应该用生命论思维（小本质、操作还原、名实相符）
2. **我是不是扣大词了？** ——分析梅卡德尔每首都套自指反自指，就是大词拜物教
3. **我是不是闭环短路了？** ——没查清楚就下结论（古月的身份、诗集名字）
4. **我是不是本本主义了？** ——照搬旧结论不做具体分析
5. **我是不是过度宣称了？** ——把猜想当事实、把启发式当定理
6. **我是不是阳亢了？** ——该沉积的时候不沉积（改完不提交）
7. **我是不是阴僵了？** ——该激活的时候不激活（用户说了才动，不主动判断）

## 四、踩过的坑（不许再犯）

| 坑 | 怎么犯的 | 怎么防 |
|----|---------|--------|
| 归属错误 | 把AI分析写进用户旁注 | 旁注只写用户原话 |
| 身份错误 | 古月=演员≠整理者 | 涉及具体人名先核实 |
| 名称错误 | 《低处飞行》写成《低空飞行》 | 专有名词先搜索确认 |
| 改得太慢 | 逐个文件Read+Edit | 批量sed，先grep看范围 |
| 重复搜索 | 同一个东西搜好几遍 | 搜过的记下来，不重复 |
| 提交不自检 | 改完直接push发现错了 | push前grep确认 |

## 五、标准操作流程（SOP）

```
1. grep/搜索 → 看清范围和数量
2. 批量改（sed/replace_all）或逐个改（Read+Edit）
3. grep自检 → 确认旧的没了、新的对了
4. git diff --stat → 确认没误伤
5. git add -A && git commit -m "说明" && git push → 一条命令提交
6. 有错误立刻改，追加到踩坑表
```
