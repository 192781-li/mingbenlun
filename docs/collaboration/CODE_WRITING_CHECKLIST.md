# 代码写作检查清单 · 生命论（明本论）项目

> 每次写代码前过一遍。不是形式主义，是让代码越写越快、越写越准的自指健康机制。
> 哲学对应：代码库是 S=f(S) 的自指系统，νF₂（活的思考）必须持续穿透 !-沉积（旧代码旧错误），否则系统会僵死。

---

## 一、写前：真问题三问（不跳这步反而更快）

- [ ] **这段代码解决什么真问题？**
  - 不是"实现X功能"，是"它对应哪个哲学命题/数学定理/具体痛点？"
  - 答不上来 = 在造 !-沉积，别写
- [ ] **有没有现成的代码可以复用？**
  - 先 grep 已有代码，先读教训库
  - 不重复造轮子
- [ ] **最小可验证原型是什么？**
  - 不要一上来写完整实现
  - 先写能跑的最小版本，验证思路对不对

## 二、写中：小步验证（工具即理论）

- [ ] **先写验证，再写实现**
  - 验证脚本不是额外工作，是逼你把问题想清楚
  - 核心定理配 Coq/验证脚本，工具脚本配单元测试，一次性脚本至少有断言
- [ ] **每写完一个小单元就跑验证**
  - 不等全部写完再测
  - 错误发现得越早，修正成本越低
- [ ] **遇到"应该能跑"的地方，强制写断言**
  - "应该" = 还没验证
  - 不验证的代码 = 猜

## 三、写后：名实审计 + 教训记录

- [ ] **名实相符**
  - 函数名、变量名、注释、文档和实际行为一致吗？
  - 有没有名实遮蔽（名字说A实际做B）？
- [ ] **条件边界标注**
  - 什么输入下成立？什么输入下会崩？
  - 不标注边界的函数是定时炸弹
- [ ] **犯了错立刻追加到教训库**
  - 这是让代码"越写越精准"的核心
  - 每次错误都变成抗体，下次不犯
  - 教训库路径：`docs/collaboration/LESSONS_LEARNED.md`

## 四、持续：自指健康检查

- [ ] **每次写代码前先读教训库**
  - 抗体先于行动
  - 不读历史就干活 = 闭着眼跳坑
- [ ] **定期清理 !-沉积**
  - 无用代码、过时注释、重复逻辑
  - 沉积不清理，νF₂ 就转不动
- [ ] **验证器本身也要验证**
  - 检查器的检查器
  - 验证脚本错了比没有验证更危险

---

## 五、快和准的关系

| 阶段 | 普通写法 | 自指健康写法 |
|---|---|---|
| 第一次 | 快（上来就写） | 慢（想清楚+写验证） |
| 第十次 | 越来越慢（和旧错误搏斗） | 越来越快（旧错误已变成抗体） |
| 第一百次 | 代码库变成泥潭 | 代码库变成武器（改起来放心） |

**准是快的前提。** 一次写对十行，比写一百行然后调试三天快得多。

---

## 六、七种坏代码习惯（碰了就错）

| 坏习惯 | 表现 | 为什么错 |
|---|---|---|
| **上来就写** | 不想清楚就敲代码 | 没有真问题的代码都是 !-沉积 |
| **写完不测** | "应该能跑"就提交 | 没验证的代码 = 猜，猜迟早错 |
| **重复造轮子** | 不看已有代码自己重写 | 浪费时间，而且容易引入新错误 |
| **不记教训** | 犯了错不改，下次再犯 | 不记录错误的体系注定重复犯错 |
| **名实不符** | 函数名说A实际做B | 名实遮蔽，后来人（包括自己）会被坑 |
| **不标边界** | 函数在什么条件下成立不说 | 不标注条件的"真理"是教条，代码同理 |
| **为优雅牺牲正确** | 为了代码好看改逻辑 | 阴主阳从，工具反过来支配目的 |
